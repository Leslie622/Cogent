# Skill Creator（技能创作与迭代指南）

用于从零创作、测试并持续打磨 Cogent 技能包（完全兼容 `agentskills.io` 开放标准）。

核心闭环只有五步：

- 搞清楚这个技能要做什么、大致怎么做
- 写出第一版 `SKILL.md` 草稿
- 用 2–3 条贴近真实场景的测试提示词试跑
- 和用户一起复盘输出结果与工具轨迹，针对性修订
- 重复迭代，直到效果满意或继续修改不再带来明显提升

加载本技能后，先判断用户当前处于闭环的哪一步：如果用户说「我想做一个 XX 技能」，从第一步开始；如果已经有了草稿或现有技能，直接进入评估与迭代。保持灵活——如果用户只想快速起草、不做正式测试，顺着用户的节奏来。

## 与用户沟通

使用本技能的用户可能非常熟悉 Agent Skills，也可能是第一次接触。注意上下文信号；不确定时用一句大白话解释术语（例如「测试提示词就是你平时真正会发给助手的一句话，用来检验技能会不会触发、效果对不对」），不要默认对方懂所有概念。

## 创建新技能

### 1. 采集意图（Capture intent）

先搞清楚用户真正想要什么。如果当前对话里已经跑过一遍值得沉淀的流程（例如用户刚手工带着你做完一件事，然后说「把这个做成技能」），**先从对话历史里提取答案**——用过哪些工具、步骤顺序、用户纠正过的地方、输入输出格式——再只就缺口向用户确认，不要把已知信息重问一遍。

需要补齐的关键问题：

1. 这个技能要让模型具备什么能力？
2. 什么情况下应该触发？用户通常会怎么表达？
3. 期望的输出格式或交付物是什么？
4. 有没有具体的输入/输出示例来锁定边界？

### 2. 确定落盘位置

Cogent 按优先级从高到低发现技能（同名高优先级覆盖低优先级）：

1. `<项目根目录>/.cogent/skills/<name>/SKILL.md`（项目私有，支持沿 `.git` 祖先目录扫描）
2. `<项目根目录>/.agents/skills/<name>/SKILL.md`（项目跨工具生态目录）
3. `<项目根目录>/.claude/skills/<name>/SKILL.md`（项目 Claude Code 兼容目录）
4. `~/.cogent/skills/<name>/SKILL.md`（用户私有，Cogent 设置页默认写入位置）
5. `~/.agents/skills/<name>/SKILL.md`（用户跨工具开放标准目录）
6. `~/.claude/skills/<name>/SKILL.md`（用户 Claude Code 兼容目录）
7. 内置只读层（`bundled`，最低优先级兜底）

选址建议：
- **仅当前仓库适用**：放 `<项目根目录>/.cogent/skills/<name>/`；如果团队同时用多款 Agent 工具，可放 `<项目根目录>/.agents/skills/<name>/`。
- **个人跨项目通用**：放 `~/.cogent/skills/<name>/`（设置页可直接编辑管理）；若希望被其他支持 `agentskills.io` 的工具共用，放 `~/.agents/skills/<name>/`。

### 3. 编写 `SKILL.md`

每个技能是一个独立目录，包含必需的 `SKILL.md`（YAML frontmatter + Markdown 正文）和可选的附属资源目录：

```text
my-skill/
├── SKILL.md          # 必需：YAML frontmatter + 精炼操作指南
└── (可选)
    ├── references/   # 长篇规范、领域文档（按需读取）
    ├── scripts/      # 可执行辅助脚本（按需调用）
    └── assets/       # 模板、样例、静态素材
```

#### Frontmatter 规范

必填字段：
- `name`：技能唯一标识。仅允许小写字母、数字和连字符（`^[a-z0-9-]+$`），长度 1–64，不能以 `-` 开头/结尾或含 `--`，且**必须与目录名完全一致**。
- `description`：说明「做什么 + 何时触发」（≤1024 字符）。这是模型决定是否调用 `skill` 工具的首要信号——**把触发场景写进 `description`，不要只藏在正文里**。模型天生容易「欠触发（under-trigger）」，所以描述要写得稍微主动一些：
  - 偏弱：`介绍如何搭建内部数据看板。`
  - 更好：`为内部业务数据搭建可视化看板。只要用户提到数据看板、指标可视化、业务报表或想展示公司内部数据时就使用本技能——即使用户没有直说「看板」。`

常用可选字段（按需添加，大多数技能只需 `name` 和 `description`）：
- `when_to_use`：补充典型触发词或使用时机（会与 `description` 合并展示在清单中）。
- `argument-hint`：输入框补全时的参数提示，如 `"[文件路径]"`。
- `disable-model-invocation: true`：仅允许用户通过 `$技能名` 或 `/skill:技能名` 手动触发，不进入模型自动清单。
- `user-invocable: false`：仅允许模型自动触发，不在用户输入框补全列表显示。
- `license` / `compatibility` / `allowed-tools`：遵循 `agentskills.io` 标准元信息字段（Cogent 保存时无损保留）。

#### 路径与参数变量

Cogent 在加载技能正文时会自动展开以下通用变量：
- `${COGENT_SKILL_DIR}`（兼容 `${CLAUDE_SKILL_DIR}`）：当前技能目录绝对路径。引用同级脚本或模板时务必使用它（如 `${COGENT_SKILL_DIR}/scripts/check.mjs`），确保在任意工作目录下都可执行。
- `${COGENT_PROJECT_DIR}`：当前会话工作区根目录。
- `${COGENT_SESSION_ID}`：当前会话 ID。
- `$ARGUMENTS`、`$ARGUMENTS[N]`、`$1`–`$9`：接收用户或调用方传入的参数。

安全边界：切勿在 `SKILL.md` 正文中硬编码任何密钥或 Token；脚本需要鉴权时应从环境变量读取。

### 4. 三层渐进披露（Progressive disclosure）

Cogent 分三层按需加载技能上下文：

1. **元数据层**（`name` + `description`）：每轮都在系统提示清单中，保持精炼（单条展示截断 250 字符）。
2. **`SKILL.md` 正文层**：触发后经 `skill` 工具按需加载，**建议控制在 500 行以内**（硬上限 100KB）。
3. **附属资源层**（`references/`、`scripts/`、`assets/`）：触发后会在技能结果里列出相对路径，由模型按需读取或执行，体积不占常驻上下文。

当正文变长时，把分场景细节拆到 `references/`，在 `SKILL.md` 里说明何时读取对应文件。例如：

```text
cloud-deploy/
├── SKILL.md            # 主流程 + 路由判断
└── references/
    ├── aws.md
    ├── gcp.md
    └── azure.md
```

正文里只需写：「如果部署目标是 AWS，先读取 `${COGENT_SKILL_DIR}/references/aws.md` 再继续。」

### 5. 写作风格

- **用祈使句，并解释「为什么」**：现代模型理解原因后执行得更稳定。当你发现自己在频繁写全大写的「必须」「绝对禁止」时，往往说明规则没讲清动机，而不是语气不够凶。
- **示例胜过空泛规则**：如果技能要求特定输出结构，直接给一个真实完整的输出样例；如果要调用特定命令或脚本，直接写出完整调用示例。

### 6. 设计测试提示词（Test prompts）

草稿落盘后，构造 **2–3 条贴近真实场景的测试提示词**——像真实用户会发的那样，带具体文件路径、口语化表达、甚至轻微省略，先给用户过目：「我准备用这几个用例测一下，要不要增删或调整？」

## 复盘草稿（Reviewing the draft）

Cogent 支持**回合边界热刷新**，写好 `SKILL.md` 后无需重启，下一轮对话即可生效。逐条试跑测试提示词：

1. 确认技能已落盘在 Cogent 发现目录中，且没有因命名或 YAML 语法错误被跳过。
2. 在新一轮对话中发送测试提示词：可以先测试模型能否凭 `description` 自动触发，也可以用 `$<name>` 或 `/skill:<name> <任务>` 强制触发测试正文质量。
3. **和用户一起看两样东西——最终结果 + 工具轨迹**：
   - 技能有没有按预期触发？
   - 输出有没有达到用户预期？哪里跑偏了？
   - 轨迹里有没有无效忙活（反复读同一个文件、临时写一次性脚本、兜圈子）？有的话通常是指令过度规定或表述含糊，**应该做减法而不是继续堆规则**。

## 迭代改进（Improving the skill）

这是整个闭环的核心。拿测试反馈改进技能时，遵循四个原则：

1. **从具体反馈中泛化**：你们只测了两三条样例，但技能未来要面对大量未见过的输入。如果某个问题反复修不好，换一种框架或心智模型重写，不要靠打补丁堆砌过拟合的零碎约束。
2. **保持正文精炼**：删掉没起作用的废话。如果某条指导导致模型做无用功，果断删掉再测一次看效果。
3. **把原因讲透**：即使用户的反馈很简短，也要提炼出背后的真实诉求并写进技能说明；讲清逻辑往往比加严厉禁令更有效。
4. **沉淀重复劳动**：如果每次试跑模型都要现写同一个辅助脚本或重复一长串固定步骤，直接把脚本放进 `scripts/`，让 `SKILL.md` 指向 `${COGENT_SKILL_DIR}/scripts/...`——写一次，复用无数次。

然后回到闭环：修改 → 重跑测试提示词 → 给用户看新结果 → 直到满意。

## 更新已有技能

如果用户要改进已安装的技能而非新建：

- **保留原 `name` 和目录名**：例如已有 `research-helper`，更新后仍叫 `research-helper`，不要另起 `research-helper-v2`。
- **遇到只读技能（如内置 `bundled` 或生态只读目录）**：不要直接改只读文件，复制到可写目录（`~/.cogent/skills/<name>/` 或 `<项目根目录>/.cogent/skills/<name>/`）再修改，利用 Cogent 的高优先级覆盖机制生效。

## 再看一遍核心闭环

- 明确目标与触发场景
- 写出精炼草稿
- 跑 2–3 条真实测试提示词
- 与用户一起看结果和工具轨迹
- 泛化、做减法、沉淀脚本
- 重复，直到好用为止
