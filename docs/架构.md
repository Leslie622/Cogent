# 架构 — Cogent

## 1. 项目定位

Cogent 是基于 Electron + [pi](https://github.com/earendil-works/pi) 的桌面 Agent 客户端，
对标主流 Agent 产品（多会话、工具可视化、审批流、设置页），**本地优先存储**。

核心架构决策（已定，不再讨论）：

- **引擎服务化**：pi 封装为独立 Node 进程（`host`），与 Electron 彻底解耦，
  通过 stdio JSON-RPC 通信 —— 任何 Node ≥ 22.19 的宿主都能复用它；
- **引擎运行时：自带官方 node22**：构建期 `npm run fetch:runtime` 下载官方
  Node 22（SHA256 对官方 SHASUMS256.txt 校验）进 `resources/runtime/<平台>/`。
  main spawn 引擎前经三级链定位（`host/runtime.ts`）：`COGENT_NODE_BIN` 覆盖 >
  自带 node22 > Electron 自带 Node 兜底（`process.execPath` +
  `ELECTRON_RUN_AS_NODE=1`，仅兜底级补设该变量）。不依赖用户系统 PATH 里的
  node（可能没装 / 版本不受控）；Electron 内置 Node 随发版走不受控（31 是
  20.15 < 22.19），自带是唯一通路。
  `COGENT_NODE_BIN` 始终是覆盖口（开发调试 / 旧宿主复用引擎时指向任意 Node ≥ 22.19）；
- **main 是壳不是业务**：窗口、IPC、引擎代理、凭据；业务（会话/工具/存储）全在引擎进程；
- **本地优先**：存储走 StorageDriver 接口，本地 JSON 先行，将来接云接口只换实现。

## 2. 一图看懂

```
Renderer（纯 UI，无 Node）
  │  window.cogent.*（preload 白名单窄接口）
  ▼ Electron IPC
Main（Electron 主进程 = 壳）
  │  窗口 / IPC 注册 / 凭据(safeStorage) / 引擎代理
  │  spawn 自带 node22（resources/runtime；三级链 COGENT_NODE_BIN 覆盖 >
  │    自带 > Electron 自带兜底，版本守卫 >=22.19）
  ▼ stdio JSON-RPC（一行一帧 JSON）
Host（独立 Node 进程 = 引擎）
  │  会话管理 / pi Agent / 工具执行 / 审批拦截 / 本地存储
  ▼ 只依赖 pi-* + protocol，零 Electron import
```

消息旅程（2026-11-06 全链路落地）：用户发送 → renderer `window.cogent.engineRequest('agent.submit')`
→ main 校验白名单 → 写入引擎 stdin → 引擎跑 pi 循环，事件流（run.* / message.delta）写 stdout →
main 转发 `webContents.send` → renderer chat store → UI。审批回路（2026-11-11 批次 2 闭环）：
写类工具挂起 → 引擎 `approval.request` 事件（同事件流广播）→ renderer 审批卡
→ `window.cogent.respondApproval` → **main 专属通道 `approval:respond`**（D3：不走
engine:request 通用代理 —— 审批是安全边界，宿主侧裁决独立成路）→ 引擎
`approval.respond` resolve 挂起的 beforeToolCall → run 续走；中止/删会话由引擎侧
signal listener / settleApprovals 兜底收口，不存在永久挂起。
偏好旅程（单向）：会话级偏好（选中模型/思考力度）落 ~/.cogent/settings.json（main 写，字段级
越界抛错、损坏记日志回默认——偏好可再生）→ 启动回填 renderer engine store。
凭据旅程：safeStorage 落盘（main，原子写）→ 握手注入（initialize.credentials）→ 引擎内存表 →
pi ModelRuntime 全内存 overlay（setRuntimeApiKey，三入口联动：initialize/credentials.set/
remove 都 await 应用后再生效；底层空 CredentialStore，绝不读写 ~/.pi 的 auth.json）。明文回流口径（2026-11-08 产品决策）：**引擎协议侧**永不回流
（credentials.list 只回布尔位）；**壳侧** credentials:get 按 provider 单取明文供设置页回显 ——
引擎边界 ≠ 壳边界，两侧勿混。凭据文件损坏/跨机器 DPAPI 不匹配不炸启动：降级为空表 +
credentials:status 暴露给设置页横幅（重存任意 key 即以全新文件自愈）；删除 key 走
credentials.remove（2026-11-10 协议新增，替代"写空串冒充删除"）。
持久化可靠性（2026-11-10，架构审查修复）：全部 JSON 落盘原子化（同目录 tmp + rename；
main 侧 storage-root.writeFileAtomic，引擎侧 JsonStorageDriver 同款——两进程按依赖方向
不共享代码，各持一份）；引擎启动恢复对损坏文件**逐文件隔离**（改名 .corrupt + stderr 记录 +
继续恢复其余），单文件损坏不再拒启整个引擎；自定义 provider 的 renderer 写路径唯一化
（只走 custom-providers:set，providers.custom.sync 已退出 renderer 白名单，防盘上/内存态分叉）。

**为什么引擎不直接进 main**：pi 要求 Node ≥ 22.19；Electron 31 内置 Node 20.15
不满足 —— 进程内集成物理不可行。服务化同时白送崩溃隔离与进程级 abort。

## 4. 集成（供将来参考）

旧 Electron 项目复用引擎 = 复用两个东西：

1. `host/` 构建产物（`out/main/host.js`，纯 ESM，靠 `node_modules` 加载 pi）；
2. `protocol/` 类型与常量（实现同一套 JSON-RPC 即可驱动）。

宿主差异只在"怎么拉起进程"：Cogent 用 main spawn 自带 node22
（resources/runtime，三级链见 `host/runtime.ts`）；旧项目同样 spawn，
用系统 Node ≥ 22.19（引擎内部零 Electron import，宿主版本无关）。
