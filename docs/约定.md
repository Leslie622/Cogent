# 开发约定 — Cogent

## 1. 代码边界与交付

### 1.1 信任边界

入口处理不可信输入和预期故障。边界内信任已经收窄的类型，尽早暴露不变量错误。合法空态、业务校验、取消、并发交接和资源清理按各自的合同处理。

| 边界 | 入口职责 |
| --- | --- |
| Electron IPC | 校验调用窗口、frame 和渠道权限，再校验负载形状与取值 |
| stdio 帧、HTTP/WS | 校验帧、方法和参数。网络入口验证身份、方法权限和资源归属。新增方法明确各入口可见范围 |
| 外部世界 | 进程、模型、工具结果和网络都有预期失败。明确超时、取消、清理和错误归属 |
| 持久化读取 | 校验版本与数据形状。损坏资料报错或旁置并留诊断。可重建的投影和偏好按各模块合同恢复 |

### 1.2 常见反模式

| 序号 | 问题 | 正确做法 |
| --- | --- | --- |
| 1 | 保存失败返回 `null` 或成功结果，或先改缓存再写盘 | 候选值提交成功后才发布；凭据加密/写盘失败保留旧值，已保存但生效失败分别报告 |
| 2 | 对已收窄的内部值重复检查类型或存在性 | 信任类型。非空、范围等业务约束由负责层校验 |
| 3 | 长链 `?.` 加默认值掩盖内部关系缺失 | 用类型表达真正的可空关系 |
| 4 | 捕获后只记录再抛出 | 由负责翻译或处理的边界记录一次 |
| 5 | 对自家常量做 `typeof` 校验 | 用类型约束常量 |
| 6 | 非法权限档静默回落到 `auto` | 拒绝非法输入并保留诊断 |
| 7 | 把判别联合断言成 `Record`，再抽查字段 | 在 `switch (event.method)` 内自然收窄 `event.params` |
| 8 | Zustand 选择器用 `?? []` 返回不稳定快照 | 集合回退用模块级 `EMPTY_*`。原始值可直接回退 |
| 9 | 把临时目录或调用方给的路径原样当真实路径做比较，或把同一物理文件的两条词法路径当成两份（主目录会话的 `<cwd>/.cogent/mcp.json` 即用户 `mcp.json`，用户服务被降级成未受信项目定义） | 先取真实路径再去重或比较。同步场景用 `realpathSync.native`：纯 JS 的 `realpathSync` 在 Windows 上不展开 8.3 短名，而 CI 的临时目录就是短名 |
| 10 | 只凭窗口 ID、文件名或 sessionId 认领异步结果 | IPC 核当前文档/frame/代次，demo 精确匹配真实路径；运行终态认 runId，旧 Host 回包核进程代次 |
| 11 | 换工作目录时把转录锚点当工具 cwd，或只清提示词缓存 | 区分本轮根快照与原 JSONL 位置；空闲交接后重建依赖目录的实例、工具和文件导航，旧回合来源不重写 |
| 12 | 把平台专属 API 当作通用 API 调用，例如在 Windows 调用 `safeStorage.getSelectedStorageBackend()` | 按平台使用宿主 API；Linux 校验 `basic_text`，Windows/macOS 只查加密可用性；补 API 缺失的对应平台回归，并以真实壳探针验证 |

### 1.3 交付自检

1. 新增守卫、捕获或默认值时说清它处理的输入或失败场景。内部不变量优先由类型和明确的状态表达。
2. Host 帧处理可从 `src/host/host-main.ts` 的 `handleFrame` 追到入口解析、守卫和参数收窄。鉴权须另外核对传输和调用者边界。
3. 按 §1.4 选择验证范围，读完整诊断并按 §1.2 核对 diff。交付说明实际运行的检查、已知失败和未验证范围；定向验证不表述为全量通过。命令、测试层和独立站检查见[测试](模块/测试.md#运行与验收)。
4. 新逻辑模块随实现带单测。验收或冒烟中发现的 bug 随修复加入行为回归，覆盖率只作观察。
5. 审查发现的反模式回填 §1.2。同类场景更新原条目，新增类别补一个代表场景。

### 1.4 验证范围

日常修改默认执行能覆盖风险的最小充分验证。范围按行为、依赖和调用链判断，不按改动行数或文件数判断；完成一次回复或小任务不自动触发四关。

| 改动 | 默认验证 |
| --- | --- |
| 纯文档、注释 | 检查 diff；Markdown 变更另跑文档检查 |
| 文案、局部样式 | 适用文件的定向 lint；涉及字号、布局或交互时追加对应专项验收 |
| 局部逻辑、常规修复 | 变更文件 lint、受影响 TypeScript 工程检查、相关行为测试；共享类型变化同时核对消费者 |
| 协议、权限、持久化、进程生命周期 | 沿调用链扩大到受影响工程、消费者及相关集成测试；影响全局时跑四关 |

- **完整四关触发条件**：用户明确要求；应用依赖或锁文件、构建/打包配置、运行时升级；全局重构或无法限定影响范围的变更；发布或计划明确要求完整验收的节点。计划中的四关要求只作用于对应验收节点，不扩展为每次小改。
- **构建按需**：源码级测试无需先 build。集成测试由现有 global-setup 检查产物新鲜度并按需构建；已有新鲜产物时不重复手动 build。真实产品链路按对应验收要求准备产物。
- **复用结果**：同一工作区与环境中，已通过检查所覆盖的源码、依赖和配置未变化时复用结果；后续修改只重跑受影响的检查。定向检查失败先读诊断，仅在发现影响扩散时扩大范围。

## 2. 协议纪律（`src/protocol/`）

- 已发布的方法和事件保留名称，字段只增可选项。破坏兼容性时递增 `PROTOCOL_VERSION`。
- 保持零运行时依赖，只放类型、常量和纯函数。renderer 消费壳契约及必要的 wire 类型，pi 运行时留在 Host。
- preload 只暴露明确的渠道。追踪契约变化时同时核对调用者、白名单、Host 注册和事件消费者。

## 3. 实现约定

- 每个文件头部简述位置和关键决策。注释用中文，解释原因和边界。引擎与壳侧讲清 pi 接线、关键决策和边界，renderer 留理解所需的说明。引用指向具体文档。
- UI 按职责拆分，优先复用。现成组件用 shadcn，聊天场景先查 AI Elements。缺少等价组件时写成可复用组件并放入 `components/`。[AI Elements](https://ui.shadcn.com/docs/ai-elements)
- 统一使用 base-nova 与组件原生 `variant`、`size`。新增形态在 `components/ui/` 定义，调用处只加布局类。外部参考用于布局结构。界面字号用 `text-xs`、`text-sm`、`text-base`、`text-2xl`，内容与代码走共享消费点。现成组件用 `npx shadcn@latest add <name>` 安装。安装细节和样式配方见[UI 布局](UI布局.md#组件库与安装)。

### 配置归属与启动纪律

- 先在负责的模块页明确语义 owner、单写者、存储位置、加载者、优先级、生效时机和就绪条件。业务共享默认由 Host 求值，客户端可显式覆盖。呈现偏好留客户端，宿主安全存储经明确协议供给。
- 引擎所需配置由启动链加载。必要配置应用后才发布就绪。启动期间的变更需要交接，跨 `await` 的工作绑定进程或操作身份。
- 先持久化再发布。已保存但生效失败时分别报告，正常读取只读取。按操作合同处理取消、资源寿命和重试。
- 配置回归覆盖无 renderer 启动、显式/项目/全局优先级、重启和迁移、写入失败，以及启动期间增删。用可控 Promise 验证顺序，扫描清单仅检查覆盖。

## 4. 文档纪律（写任何 docs/ 文档前）

文档内容与文件名用中文，技术术语保留原名，`README.md`、`AGENTS.md` 等标准文件名保留。

| 文档 | 唯一归属 |
| --- | --- |
| [架构](架构.md) | 当前进程、跨模块数据流、目录、构建、reference 克隆方式 |
| [模块](模块/索引.md) | 模块现状、源码入口、边界、关键行为和验收 |
| [UI 布局](UI布局.md) | 区域代号、视觉与组件配方 |
| [约定](约定.md) | 代码、测试义务和文档规则 |
| [技术笔记](技术笔记/索引.md) | 原理、源码对照与取舍 |
| [决定](决定.md) | 容易误改的取舍（含架构级）及被否方案索引，正文回到对应归属 |
| [计划](计划/全局架构.md) | 目标、未完成队列、实施方案和审查证据 |
| [测试用例](测试用例/) | 手动触发步骤、验收证据与未测范围 |
| [架构地图](架构地图/README.md) | 交互式目标接线、能力状态和源码入口 |

- 事实文档只写当前实现，目标、已知差距和待验证结论放计划。模块关键行为带「验收：」。会话状态和异步链路用简图说明 owner 与事件顺序。
- **架构地图同步门槛**（`docs/架构地图/`）：内部重构、局部 UI 调整、Bug 修复及过渡态改动不触发改图；仅在增删进程/传输通道/核心服务/存储域、`#planned` 能力正式收口、或身份认证/审批/MCP/技能/钩子主流程稳定变更时同步地图，并确保通过 `保真校验.test.ts`。
- 完成计划后把现状、原理和未完成边界迁回所属文档，更新引用并移除过程稿。历史由 Git 保存。
- 同一事实保留一个正文，其余用链接。写索引时提供查找入口。架构、约定、UI 布局通常 150–250 行以内，模块通常 40–80 行。过长先归位、压缩，再评估拆分。
- 验收册记录命令、环境、结果和未测范围。可以重跑的日常日志和通过明细放 `tmp/`。仓库保留后续仍要比较的原始样本和夹具来源。
- 引用 `reference/` 参照仓时写短 SHA（至少九位）和文件出处，版本以根目录 `reference.lock.json` 的当前钉板为准；钉板前移后旧对照只用于原范围，保留的行内标注年月（如「2026-11 实读」）表明是历史实读。钉板与更新命令见[架构](架构.md#reference-源码参照)。
- 可机检的部分由根 `npm run lint` 执行：链接、锚点、入口可达性和带文档名的章节引用缺失即失败，行数超出上述预算和指向历史钉板的参照引用只提示。范围见[测试](模块/测试.md#运行与验收)。
