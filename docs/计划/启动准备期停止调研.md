## 1. 结论

这是确定的信息丢失与预约缺口，可以在现有Host及pi公开接口上修，不需要更换引擎。
但此前“stopRequested + prompt前检查 + agent_start接力”的草案只描述了取消主线，
没有覆盖用户输入持久化、续写旧正文、handled分支与迟到RPC；不能直接按几处判断动工。

推荐优先修此正确性问题，再继续工具封段重挂等UI专项。最小可靠范围包括submit、
手动continue和manual compact准备期，以及同一条异步链的删除失效；不新增总调度器。

## 2. 本地窗口与owner

```text
Host受理/预约（忙判定的owner）
  -> ensurePiSession -> setModel -> pi.prompt的input/auth准备
  -> pi._prepareRun / before_agent_start -> core agent_start -> provider
  -> agent_settled -> 唯一终态 -> 释放预约

abort必须先记在Host的本次操作上，再交给已存在的pi取消入口
任一await返回：检查会话仍在、本次owner仍有效、是否已经请求停止
不可取消的await尚未结束：保持预约，不能让旧链混入新run
```

| 窗口 | 本次实读出处 | 缺口 |
| --- | --- | --- |
| submit装配/切模型 | `src/host/runtime/session.ts:945-953,976-1003,1137-1143` | submit已预约StreamingState，但abort不保存准备期意图；pi未装配时请求被丢弃，随后仍prompt。 |
| 手动continue装配 | 同文件 `1052-1084` | busy检查后首个await之前没有预约；第二个submit/continue/compact可通过，abort也可能没有目标。 |
| manual compact装配 | 同文件 `1109-1117,1137-1143` | compacting已预约，但pi不存在时没有取消意图，装配后仍会compact。外部agent.abort能触发，不因UI缺按钮忽略。 |
| 删除期间装配完成 | 同文件 `756-780,1425-1438` | 删除只dispose当时已有pi；旧装配返回后仍可能写旧对象并继续prompt，需回收失效结果、阻止后续执行。 |

## 3. pi的真实取消边界

实读 `reference/pi` 的 `74dcca7` 与已安装pi 1.5.2；探针使用项目自带Node 22.23.5。

| pi窗口/入口 | 源码出处（pi根目录内） | 已确认行为 |
| --- | --- | --- |
| input/auth preflight | `packages/coding-agent/src/core/agent-session.ts:2186-2262,2598-2617` | preflight计数已增加，但isStreaming=false、isIdle=true；abort不记run标记，可以先返回，释放准备钩子后仍正常执行。 |
| before_agent_start | 同文件 `1943-1948,1996-2020,1164-1167` | run已active，原生abort会记意图；后续agent_start内置接力。不能把所有准备阶段笼统说成原生abort均无效。 |
| preflightResult | 同文件 `325-339,1943-1969`；`packages/coding-agent/src/modes/rpc/rpc-mode.ts:409-433` | 导出的PromptOptions没有signal，有官方RPC使用的internal回调handled/queued/started。started在准备完成后、core prompt前同步调用，可补pi.abort。 |
| agent_start公共监听 | `agent-session.ts:1100-1103,1207-1209`；`packages/agent/src/agent-loop.ts:126-133` | 同步公共回调能将core信号设为aborted；但loop不会因此通用跳过streamFunction。 |
| prepareRequest | `packages/agent/src/agent.ts:216,493`；`agent-loop.ts:228-236` | 公开可链式包裹；原hook前后检查signal可提前结束已取消请求，异常在Agent生命周期内正常转成aborted消息/turn_end。必须保留pi原hook。 |
| handled/前置拒绝 | `agent-session.ts:2169-2176,2206-2215,2268-2291,1947-1954` | prompt可不启动run便返回，也可能准备阶段拒绝；不保证agent_settled，Host不能只等该事件。 |
| manual compact内部起跑 | `agent-session.ts:2923-2926,3073-3075` | compact先await abort，再建压缩controller并发compaction_start；仅调用前检查仍有窗口。manual compaction_start时可按本次owner补abortCompaction。 |

不要在preflightResult的started回调里throw阻止启动：onStarted在生命周期try/finally
之前执行，可能绕过settled并留下active标记。该回调只补取消，不抛异常。

input/before_agent_start处理器没有贯穿的AbortSignal，异常也可能被runner记录后继续
处理（`packages/coding-agent/src/core/extensions/runner.ts:1434-1483,1532-1570`）。
不能宣称立即杀掉任意准备Promise；应立即记录停止，并在安全边界阻止后续模型工作。

## 5. 两处数据合同与迟到RPC

**已提交用户输入。** Host受理时只改summary和运行账本；用户直到pi message_end才进入
转录。准备期直接return会留下“界面有问题、树里没有问题”的不一致。已用安装版公开API
验证：sessionManager.appendMessage(user) + refreshContext，在不prompt的情况下即可
写入live context和JSONL，重开仍有user。源码依据 `session-manager.ts:1168-1193,1222-1232`、
`agent-session.ts:1505-1507`；本地旧转录导入也使用这些API。

这是可行候选，不代表可在仍运行的pi preflight中随意改树：只有确认本次输入没有交给pi、
旧准备链已收敛且仍持有owner时才可补入；已由pi正常交付的user不可再次追加。装配完全失败
时还需明确输入回滚/失败重试语义，不能谎称已持久化。证据：`准备期用户持久化验证.json`、
`prep-user-persistence.mjs`，均在上述忽略目录；独立临时目录，没有用户数据。

**手动续写旧正文。** renderer continue不追加user（`stores/chat/store.ts:346-365`）；
replaceRunTerminal替换最后user后的整个区域（`stores/chat/flatten.ts:94-119`）。
实调产品纯函数确认：早停给messages=[]会删旧截断前缀；只给新增尾段也会替掉旧前缀。
无新增内容早停可缺席messages以保留现有回答；正常续写须明确原回答与新尾部的完整替换
范围。当前Host空segments起步也有这条相关边界；本轮证据是源码值链+真实替换函数，
尚未跑完整Host/pi续写集成。证据：`准备期续写快照验证.json`、`prep-continue-snapshot.mjs`。

**长RPC迟到。** `host-main.ts:467-474,837` await continueSession，其到prompt/settle完成
才返回。若stopped后旧链reject并rethrow，renderer原continue catch仍可能覆盖结果或新run。
现有stopRequestId只保护abort回包。候选优先保持响应合同、增加本次run请求身份并使取消
正常返回；另一个选项是continue改为受理即回，但需明确ok语义变化，不能暗改。

## 6. 候选修复与验证范围

1. submit/continue首await前捕获本次操作身份与stopRequested，continue预约覆盖校验期；
   manual compact保留自己的排他owner并记录同样的取消意图。沿用现有运行账本，不造队列。
2. abort先记意图，再调用已有pi取消入口。每个await返回后核对owner/删除/取消，再做
   下一步；准备链尚未收敛时保留预约。界面可以显示“正在停止”，不能假装后台任务已结束。
3. prompt使用preflightResult观察started/handled/queued，started仅补abort；是否追加
   prepareRequest链式检查按上表收益采用。manual compaction_start补发其独立取消。
4. submit早停保证用户输入live/落盘/重开一致；continue早停保留已有正文，正常续写也不丢
   前缀。唯一终态采用前批reason合同，但messages字段是否在场由真实替换范围决定。
5. continue请求拒绝回写按本次run身份隔离；取消与真实准备错误分开，不能因为点过停止
   就把不相关装配故障伪装成成功中止。删除后晚到pi实例不得起跑，并回收本实例。

动工前还需定稿两项对外行为：continue在校验期预约时是否立即发run.started，以及装配
完全失败时乐观用户输入如何反馈。当前没有必须增加新协议事件或新依赖的证据。

验收必须使用可控Promise卡住装配、setModel、input/auth、before_agent_start、compact
内部起跑；观察真实端点请求数、唯一终态、busy排他、旧owner不污染新run。另验user恰一份
且能重开、continue前缀保留、handled不会永久running、装配失败/取消竞争、删除期间装配
返回、迟到continue拒绝、A/B隔离。此处是待实施矩阵，不是已通过的产品回归。
