## 1. 目标与范围

三件交互工具，全走 pi 的 customTools 注入缝 + Cogent 既有挂起/回填骨架：

1. **todo_write（任务清单）**：模型维护任务清单（全量替换语义），
   UI 呈现进度条目，压缩/重启后不失忆；
2. **ask_user（结构化提问）**：模型卡在需要人拍板处，弹结构化问题
   （选项/多选/自由输入）挂起等答，答案回灌模型继续跑；
3. **plan 闭环（enter_plan + submit_plan）**：模型可主动进 plan 档
   （只收紧）；plan 档完成调研后调 submit_plan 提交方案 → 方案审批面板
   （批准含切档选择 / 拒绝可附反馈）→ 批准后切执行档 + 方案回灌 +
   压缩不丢；拒绝无反馈即停轮。

**零新增审批链**：三件工具在 tool-meta 里 kind='read'（会话内交互，
无文件/进程副作用）→ `decideApproval` 直接放行（含 plan 档）——
它们的"审批"就是各自的面板，与工具执行审批链正交。挂起原语不新造：
镜像 `pendingApprovals`（session.ts:451）三件套——pending Map +
北向事件 + respond 方法 + signal abort 收尾 + 会话删除收尾。

**对咨询会话的一处修正**：会话里说「customTools（agent-session.ts:276），
Pi-meme 的 subagent 就是走这条缝」。前半正确；后半经本轮核实**不成立**——
Pi-meme 全仓 `grep customTools` 零命中，它走的是 `InlineExtension` +
`pi.registerTool()`（pi-adapter/session-worker.ts:202-211 收集扩展、
:340 `configureInlineExtensions` 注入）。两条缝都真实存在（registerTool
定义在 extensions/types.ts:1717），Cogent 选 **customTools**：三件套是
Host 固有能力，配置期静态声明即可，比 InlineExtension 少一层扩展
生命周期；动态注册能力（按会话装卸）暂无需求。

## 3. 设计

### 3.1 注入骨架（三件共用）

```
src/host/runtime/interact-tools.ts   ← 新文件：TypeBox schemas +
  createTodoTool/createAskTool/createPlanTool（接收 InteractBridge，
  ApprovalBridge 同款手法——挂起/状态语义住 session.ts）+
  InteractBridge 接口定义
src/host/kernel/pi-session-factory.ts  ← PiSessionOptions 加
  customTools?: ToolDefinition[]，透传 createAgentSession（薄缝）
src/host/runtime/session.ts           ← buildPiSession 构造三件工具
  （闭包捕获 session/notify）传入；实现桥方法：
  pendingQuestions/pendingPlans Map、respondQuestion/respondPlan、
  settleInteractions（删除/退出收尾）、todos 状态与 section 源
src/host/runtime/tool-meta.ts         ← 白名单 + TOOL_METAS 三条
  kind:'read' + resultSummary 生成器；toolDeclarations() 补三件
package.json                          ← typebox 声明为直接依赖
```

- **挂起流程（ask_user 为例）**：模型调 ask_user → kind=read 放行 →
  execute 进 InteractBridge.ask(questions, signal) → session.ts 登记
  pendingQuestions + notify('question.asked') → Promise 悬着（工具不落
  结果，run 不结束）→ 宿主 `question.respond` → resolve(answers) →
  execute 返回结果文本（三态格式化）→ pi 落 toolResult 进转录 → 模型
  下一轮看到答案。abort/settle 双收尾同 pendingApprovals；
- **submit_plan 同构**，载荷从 questions 换 plan 全文，批准路径多一步
  setPermission + StoredSession.plan 落账；
- **事件时序**（owner 图，硬规则 5）：

```
pi 内核                session.ts(桥)              宿主(renderer)
  │ 模型调 ask_user       │                           │
  │→ tool_execution_start ─→ tool.started 事件 ───────→ 工具卡(running)
  │ (beforeToolCall 放行)  │                           │
  │ execute() ────────────→ 登记 pending + ───────────→ question.asked
  │   await 挂起           │  notify('question.asked')   └ QuestionPanel
  │                        │ ←──── question.respond ──── (替换输入区)
  │                        │  resolve(answers)            │
  │ execute 返回结果        │                           │
  │→ tool_execution_end ──→ tool.completed ───────────→ 工具卡(ok+答案摘要)
  │ (转录落 toolResult)     │                           │
```

### 3.2 todo_write

- schema：`todos: Array<{content: string(1..), status: pending|
  in_progress|completed, priority: high|medium|low}>`，additionalProperties:
  false；description 写明**全量替换**、尽量单 in_progress、完成即标
  completed、每完成一件/新增任务即更新；
- execute：桥回调更新 Session.todos + persist（StoredSession 私有字段）
  + notify('todos.updated', {sessionId, todos}) → 返回结果文本 =
  编号清单 + 计数摘要（zcode formatTodoStateForModel 同风格）；
- 模型可见性双通道：转录里的工具结果（恢复回放）+ cogent_todos 段
  （before_agent_start 每回合，非空才设；空清单=缺键撤段——技能座同款
  空墓碑语义）；
- UI：TodoStrip（清单非空挂载，可折叠；条目三态图标 + priority 配色）
  + 工具卡走既有通道；恢复：`session.messages` 响应 additive 带 todos
  （StoredSession 读取，惰性会话零装配成本）。

### 3.3 ask_user

- schema：`questions: Array<{question: string, header?: string(≤12),
  options: Array<{label, description?}>(2..4), multiSelect?: boolean}>(1..4)`；
  禁止选项 label 重复/自带「其他」（zcode 72-89 同款校验，schema 层
  superRefine 等价实现）；
- execute → 桥挂起 → `question.asked` 事件（载荷 = questions 全文）→
  宿主 `question.respond {requestId, answers: Array<string | string[]>}`
  （按问题序；多选=数组；面板「其他」自由输入=字符串）；
- 结果文本三态（zcode handlers:131-158 风格）：全答=「用户已回答：问=答…」；
  空答=「用户未作答，请自行判断」；部分=明示跳过数；abort=「用户取消了
  回答」；多选数组以「；」连接；
- 面板：ApprovalPanel 母版（替换输入区）——逐问标题 + 选项钮（单选
  即点即答本问，多选勾选+确认）+「其他」输入框常驻 + 整卡确认钮。

### 3.4 plan 闭环（enter_plan + submit_plan）

- **enter_plan**：无参；execute → setPermission('plan')（幂等：已在此
  档直接成功）→ 结果文本 = 已进入 plan 档 + 工作流指引（先调研，完成后
  submit_plan）；
- **submit_plan**：`{plan: string(1..20000)}`（zcode 上限同值）；非 plan
  档 → isError + 指引文本（zcode handlers:67-77 同款「此工具仅用于
  plan 档提交方案」）；plan 档 → 桥挂起 → `plan.requested` 事件（载荷
  = plan 全文）→ 宿主 `plan.respond {requestId, approved,
  switchMode?: 'ask'|'auto'|'autonomous', message?}`：
  - **批准**：setPermission(switchMode ?? 'ask') + StoredSession.plan
    落账（sessionId、plan 全文、批准时刻）+ 结果文本「计划已批准，从
    待办清单开始执行。\n\n## 已批准的计划：\n{全文}」+ cogent_plan 段
    持续注入（文案尾部带「若已完成或不再相关，忽略之」——zcode plan
    文件提醒同款语义）；新批准覆盖旧 plan；
  - **拒绝无反馈**：isError「用户未批准该计划」+ `terminate: true`
    停轮（控制权交还用户继续对话）；
  - **拒绝带反馈**：isError +「用户未批准该计划。用户指示：{反馈}」
    （截断上限同 APPROVAL_MESSAGE_MAX_CHARS）——模型修订后重提自然
    触发新一轮审批；
- **plan 档提示词**：permissionSectionText('plan') 扩写——只读约束
  （既有）+ 工作流（调研 → 疑点用 ask_user 澄清 → submit_plan 收尾；
  不要用普通文本问「这个方案行吗」，那正是 submit_plan 的职责）。

### 3.5 协议（全部 additive）

```ts
// 方法（与 approval.respond 同档；注册表 host-main + 白名单
// main/ipc/engine.ts + env.d.ts 镜像，技能座同流程）
'question.respond': { params: { requestId; answers: (string|string[])[] };
                      result: { ok: true } }
'plan.respond':     { params: { requestId; approved: boolean;
                      switchMode?: 'ask'|'auto'|'autonomous'; message?: string };
                      result: { ok: true; summary?: SessionSummary } }
// 事件
'question.asked': { sessionId; requestId; questions: [{question; header?;
                   options: [{label; description?}]; multiSelect}] }
'plan.requested': { sessionId; requestId; plan: string }
'todos.updated':  { sessionId; todos: TodoItem[] }
// SessionMessagesResult 加 optional todos；StoredSession 加私有字段
// todos / plan（版本号不动——缺省字段向后兼容）
```

- 配对错 requestId → InvalidParams（respondApproval 同款，防双击/竞态）；
- 会话删除/退出：settleInteractions 把挂起 question/plan 全部收尾
  （question → 空答结果；plan → 拒绝结果），settleApprovals 旁同点调用。

## 4. 边界（明确不做与归属，硬规则 9 逐条给墙）

| 项 | 判定 | 理由（真实的墙） |
| --- | --- | --- |
| ask 5 分钟自动继续（zcode interaction-registry.ts:30-31） | **不做** | 那是后台/多会话代理场景的兜底（用户不在屏幕前）；Cogent 桌面单用户前台，挂起时输入框即停止钮（abort 通道既有）。自动替答 = 没看到问题就被作答，制造事故面而非收益 |
| ExitPlanMode 的 allowedPrompts 预授权声明 | **不采** | zcode 全仓无消费者（grep 仅 schema 定义与出参透传）；Cogent 审批规则粒度是 ToolKind 级（ApprovalRegistry 语义），参数级预授权要重建规则模型。无消费点 + 模型不匹配 |
| 选项 preview（HTML 片段预览） | **不做** | zcode 为此写了 HTML fragment 安全校验器（ask-user-question.ts:222-250 禁 script/style）——安全成本实在；v1 选项 = label+description 已覆盖决策场景 |
| TodoRead 工具 | **不做** | 模型可见性双通道（转录工具结果 + cogent_todos 段）已闭环；TodoRead 是 zcode SQLite 架构下"工具结果可能被挤掉"的补丁，Cogent 无此缺口 |
| 挂起请求 1s 重发恢复（zcode broker） | **不采** | zcode 反向 RPC 宿主可能只从快照恢复（丢请求要补发）；Cogent 事件流 stdio/WS 直连必达，重连由传输层管。通道性质不同 |
| plan 落盘用户工作区（.zcode/plans/plan-\<sid\>.md） | **不采** | 目的（compact 后不丢）由 cogent_plan 段等价达成且更及时（段每回合在场，文件要 compact 触发重读）；往用户项目目录写计划文件是工作区污染，Cogent 会话域已有存储位 |
| cogent_plan 段手动清除钮 | **不做** | 段文案自带"已完成或不再相关则忽略"（zcode plan 文件提醒同款语义），误导面已封；清除钮 = 新方法+UI+store 三件，收益被文案覆盖 |
