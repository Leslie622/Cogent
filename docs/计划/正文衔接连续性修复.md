# 正文衔接连续性修复

> 对话流畅性剩余清单第 1 项（交接 §22）。调研范围经用户裁决收窄为只对照
> zcode（2026-11-18）。本文为目标 / 对比结论 / 设计 / 边界 / 验收，
> **用户审批通过后才动代码**。

## 1. 问题与目标

模型先出文字再调工具时，store 做「封段接力」：流式占位（id `'streaming'`）
改名 `live-${uuid}` 归为过程段，另建新占位。呈现层随之连锁重挂：

| 缺陷 | 位置 | 后果 |
| --- | --- | --- |
| 封段换父容器 | `TurnGroup.tsx:103-108` live 分支：过程项在过程容器 div（`:338-344`）内、流式正文占位在容器外（`:345-349`）；封段后旧段挪进过程容器 | 已有正文 MessageRow/Markdown 整体重挂：渐显中断、文本选择丢失、滚动微跳 |
| 封段改 id | `events.ts:34-35`（工具启动）、`:404-405`（中止收尾）改名；渲染 key=`item.id` | 即使位置不变，key 变也重挂；`HomeChat.tsx:245` 无 user 兜底组 key=`items[0].id`，首项被封段改名时**整组** remount（含 WorkingLine 计时） |
| id 承载状态 | `MessageRow.tsx:142,147`、`TurnGroup.tsx:105` 用 `id === 'streaming'` 判活跃占位 | 状态与身份耦合，是上两条的根源 |

目标：**封段时正文行零重挂**——同一 DOM 节点、同一父容器、同一 key；
无 user 组不整组重挂；运行中不再存在其他重挂源（核实结论见 §3.3）。

## 2. zcode 对比结论（本次实读，仅 zcode）

| 机制 | zcode 出处 | 要点 |
| --- | --- | --- |
| 容器按位置，不按状态 | `reference/zcode/packages/ui/src/v4/conversationTimelineLiveTail.ts:50-59` | 注释记载同型 bug：「曾按 isRunning 切换父容器，Stop 后整轮重挂……**以轮次位置决定容器，让终态沿用已有组件**」。轮内（含工具启动）永不换容器；旧轮只在**新一轮出现**时进虚拟历史，那时已终态 |
| 轮 key 只依赖稳定 id | `conversationTurnRenderUnits.ts:337-339` | 「虚拟列表 key 必须只依赖协议稳定的 turnId」 |
| 行 key 终身不变 + 重分组续 key | `ConversationTurnGroup.tsx:714-718`（flowItems 按 rowId 出 key）、`:639-666`（`useContinuousGroupKeys`：重新分组时新组按 rowId 成员**继承**旧组 key） | 身份跟着内容走，不跟位置/归类走——Cogent 封段改名正违反此条 |
| 运行中过程恒平铺 | `ConversationTurnGroup.tsx:731`（`open = turnRunning \|\| …`）、`:742-810`（过程行与正文行同一 Collapsible 平级列表，工具启动只是尾部追加 flow item） | 不存在「正文位 / 过程容器」分家 |
| 解析模式不参与身份 | `message.tsx:1386-1387` | 「streaming/static 只是解析模式，不应参与 React key；否则……卸载整棵 markdown 子树，让已显示的正文重新触发淡入动画」——与 Cogent `id === 'streaming'` 驱动 Markdown streaming 同型反模式 |

结论：Cogent 的问题不是缺新机制，而是两条既有反模式（状态写在 id 上、
按归类分容器）。zcode 的对应修法都可平移。

## 3. 设计（最小修复，两刀 + 一项核实）

### 3.1 store：占位身份与状态分离

- `MessageItem` 增 `placeholder?: boolean`；
- 占位创建（`store.ts:104-109`）：id 改为 `crypto.randomUUID()` 一次分配
  **终身不变**，同时 `placeholder: true`；
- 封段接力（`events.ts:29-35`）与中止收尾（`:404-408`）：置
  `placeholder: false`，**不改 id**；后续正文开新占位（新 uuid）；
- 全部 `id === 'streaming'` 特判改读 `placeholder`：
  `TurnGroup.tsx:105`（splitTurn live 判据）、`MessageRow.tsx:142,147`
  （Reasoning running / Markdown streaming）。

### 3.2 渲染：live 列表拉平

TurnGroup live 分支：过程项与流式正文占位进**同一个** flex 列表容器
（沿用 `gap-3 pr-1`），WorkingLine 仍随其后。封段在列表视角 = 原项
`placeholder` 翻 false + 尾部追加新占位——**key / 父容器 / 位置三不变**，
React 全程复用同一节点。

`HomeChat.tsx:245` 组 key（`items[0].id`）**不改**：3.1 落地后首项 id
不再因封段变化，组 key 天然稳定；补无 user 组封段回归测试钉住。

### 3.3 来源信号核实（不新做机制）

3.1+3.2 落地后，运行中的重挂源逐项核对：

- 封段重挂：本批消除；
- 终态收进 RunTrace 折叠体：重挂发生在 `running=false` 之后，Markdown
  `streaming=false` → 全 settled，不重播（§15 收尾批已保证）；
- 快照 / 切会话 / 非前缀替换：`isIncrementalRevealSource`
  （`stream-reveal.ts:153-155`）已防旧文重播。

若手测仍见运行中重播，另立小批，不在本批扩机制。

```text
owner: chat store（消息身份：id 终身稳定 + placeholder 表活跃）
       / TurnGroup（容器按位置：live 单列表，不分家）

delta → 占位 content 增长（id/key 不变，React 原地复用）
tool_start / abort 封段 → 旧段 placeholder=false（id 不变）
  → 工具项 append → 新占位（新 uuid, placeholder=true）append
  → 同一列表：旧段 DOM 原地保留，零重挂
run 终态 → running=false → 过程收进 RunTrace
  （此处重挂但 streaming=false，settled 不重播）
```

## 4. 边界（真实的墙）

- 不动协议 / Host / 引擎；纯 renderer store + 呈现层；
- 拉平后流式正文行获得与过程行一致的 `pr-1`（4px 右距；终态 answer 无）
  ——真机验收时核对，若有感再把 `pr-1` 移到过程项自身；
- `'streaming'` 字面 id 从代码消失；占位本就不持久化，无历史迁移问题；
- 既有测试多处以 `id:'streaming'` 为合同——**同步改合同**，不许删测试规避；
- 本批不做代码/表格行级过渡（清单第 2 项）、不做虚拟化（第 3 项）。

## 5. 验收

自动（先红后绿）：

1. 封段（工具启动 / 中止）前后正文行**同一 DOM 节点**（jsdom：
   `querySelector` 同引用断言）；
2. 无 user 兜底组封段不整组重挂；
3. 占位 `placeholder` 合同（创建 / 接力 / 中止 / continue / 快照替换）
   的 store 回归；
4. 相关 render 测试 + 全量 `npm test` + lint / typecheck / build 全绿，
   完整输出已读。

手测（真机 Electron31，用户复验）：

1. 长正文输出中途触发工具：正文无闪烁、无重播、选择不丢，计时与滚动连续；
2. 半截中止后再发新消息：旧段原地保留，无整组重挂痕迹；
3. 无 user 历史尾部（D9 压缩兜底组）封段不跳。

## 6. 实施与验证记录（2026-11-18）

实现与 §3 设计一致：`ChatMessage` 增 `placeholder`（env.d.ts，renderer 本地
字段）；占位创建用 uuid（store.ts 合帧写入）；tool.started 与中止收尾封段只翻
布尔（events.ts）；TurnGroup live 全项平铺、正文段 key = 回合内段序数；终态与
live 共用同一容器使终答行跨终态保留旧 DOM；MessageRow 流式态改读 placeholder。
实施中发现的必要细节：终态侧 RunTrace/终答必须与 live 项在**同一容器**且都带
显式 key —— 条件 Fragment 包裹会让容器子级结构不可对齐而全量重挂（§15 交接
依赖的位置匹配对 key 空间敏感）。

- 红灯验证：临时 jsdom 探针在旧代码上复现封段换节点（同一节点 = false），
  探针删除后以正式回归重建（TurnGroup 封段前后同节点；HomeChat 经真实事件
  订阅的同节点回归）。
- store 合同：tool.started 封段 id 不变 / placeholder 翻 false；中止封存同理；
  真失败移除占位（store.test / delta-batcher.test 更新 + 新增）。
- §15 终态交接由既有 turn-terminal 10 项真组件回归守住（新结构下全过）。
- lint / typecheck / build 全绿；npm test **55 文件 529 项全过**（+3 新回归）。
- 边界如实记录：终态权威快照替换正文段 id、或快照段数与 live 占位数不齐的
  边角仍换 DOM（settled 不重播）；live 的 thinking-only 中间段改经 MessageRow
  呈现（Message 壳内 Reasoning，与活跃占位一致；原先经 ProcessItem 为裸
  Reasoning）。
- 真机复验待用户：长文流式选中文字 → 工具卡出现，选区不丢；带代码块正文
  封段高亮不闪灰（复现条件见 §5）。

## 7. 续作：段间排期接力（2026-11-18 用户复验反馈）

零重挂交付后用户反馈新观感问题：封段后旧段渐显按 §15 自然放完（≤550ms），
新段是全新 Markdown 实例、排期时钟从 -Inf 起、首拍即起 —— 快工具（<排期尾）
场景两段渐显倒序并存。属本批修复暴露的既有隐患（修复前封段重挂成静态，
两段从不并存）。

修法（最小）：`StreamingRevealPacing` 共享种子（`{ minStart }`）——
ChatMessages 按活动会话创建、经 `RevealPacingContext` 下发；Markdown 挂载时
以 `minStart` 为初始时钟，`commitStreamingReveal` 把「末拍起跳 + 300ms 淡入」
发布回种子。语义 = 新段首拍不早于前段**淡入完整结束**（对齐用户表述
「上一段完成，下一段再开始」）；慢工具零影响（start = max(now, clock+interval)）；
无 Provider 的独立渲染行为不变。`REVEAL_FADE_MS=300` 与 globals.css
`--reveal-duration` 双处常量，漂移只造成观感差。

验证：stream-reveal 纯函数新增 3 项（发布/消费、无种子不变、过期种子不等）；
lint / typecheck / build 全绿；npm test **55 文件 532 项**全过。若用户更想要
「瀑布式」衔接（新段对齐前段末拍**起跳**而非淡入结束，与段内尾巴美学一致），
去掉发布处的 +REVEAL_FADE_MS 即可，一常量之差。

复现条件（短纯文本无感，2026-11-18 实测）：封段重挂在「动画已放完、
无选中、无代码块」时视觉无感——内容与位置在同一帧内近似不变。可靠
信号：① 流式中**选中**已输出文字，工具卡出现瞬间选区消失（DOM 被换
的实锤）；② 正文含代码块时高亮被打回灰底重算闪变。手测 1 须用长文
+ 选中法或带代码块的提示词。
