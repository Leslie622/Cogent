## 1. 结论与证据范围

真实 Cogent 组件在 Electron 31.7.7 / Chromium 126.0.6478.234 下，可以通过两个开关
稳定复现或消除流内时钟图标的换行微抖：视口 `contain: content` 与内容 `translate`
残差补偿。只撤视觉副本不够；同时禁用这两项后，保持原有小数行高、Markdown、
时钟图标、滚动壳、RO 贴底与渐隐蒙版，流内图标的连续截图可逐像素一致。

Zcode 对应 timeline 视口不设该 containment；贴底直接写 scrollTop，不做上述内容平移。
这是一条已经用干预实验支持的实现差异，不能再把差异归结为技术栈、环境幸运或无解。

边界：测的是本机真实 Electron 中复用产品组件的隔离页，不是用户当前运行的 Zcode
桌面版本，也不是完整 Cogent 窗口的全路径验收。没有 GPU trace，不能进一步声称已定位
Chromium 内部某个具体 bug。当前带副本的组件在本次实验同样稳定，不能宣称已复现
用户所有日常使用中的抖动。

## 2. 两边源码的具体差异

| 项 | Cogent | Zcode |
| --- | --- | --- |
| 视口绘制隔离 | `src/renderer/src/components/ui/message-scroller.tsx:423` 带 `contain-content`，即 `contain: content` | `reference/zcode/packages/ui/src/v4/ConversationTimeline.tsx:2033-2045` 无此项 |
| 贴底后平移 | 同 Cogent 文件 `:99-103` 清 translate、滚到底、测残差、再设置内容 translate | 同 Zcode 文件 `:1177-1189` 写 scrollTop 后回读记账，无此平移 |
| 内容增高回调 | 同 Cogent 文件 `:194-196`，RO 直接调用 pin | 同 Zcode 文件 `:1327-1376`，live tail 的 RO 同步吸底，注释明确防止正文先顶走 loading 槽 |
| 正文默认行高 | `globals.css:556` 默认 1.625，14px 字号下为 22.75px | `components/ai-elements/message.tsx:2003` 为 1.75；`lib/uiFontSize.ts:3` 默认 14px，故默认 24.5px，字号允许调整 |
| 活动轮布局 | MessageScrollerItem 流内布局 | `ConversationTimeline.tsx:2151-2180` 为独立 live tail；`:924` 明确不参与 virtualizer 测高 |
| 高度取整 | 不作为当前跟随策略 | 同 Zcode 文件 `:259-264` 的取整用于测量/缓存；live tail 的 cacheHeight 只写缓存，不能外推为它把活动 DOM 高度取整 |

Zcode `ConversationTimeline.tsx:1231-1281` 还在历史列宽变化时同步提交测高，再吸底，
避免使用旧占位高度。不能仅截取 scrollTop 赋值那一行就概括为“Zcode 没有防抖处理”。

## 3. 实验方法

所有脚本和原始 JSON/PNG 位于 `tmp/zcode-jitter-research/`，未修改产品或 reference。

- 最小页 `probe.html`：确定性追加文本，固定工作行，分别切换行高、贴底算法和 containment。
- 真实组件页 `product/app.tsx`：直接 import 产品 `MessageScroller*`、`Markdown`、
  `WorkingLine` 和全局 CSS；显式添加 Tailwind 源码扫描，确认 contain-content 等规则真实生成。
- 视觉副本消融通过实验页 CSS 隐藏副本、显示源；组件及其 effect 仍存在。
  补偿消融通过 `translate:none!important` 阻止平移生效；正式删代码尚未进行。
- 每次追加后等待三次 rAF，再由 Electron capturePage 获取稳定截图；图标使用固定裁框，
  比较完整 BGRA 字节 SHA-256 和 `255 − RGB均值` 加权纵向重心。
  不是在内容持续改写时把任意截图当成同一测量相位。
- 每条件连续追加八次。首轮暂停 CSS 动画以隔离图标，后续恢复正文渐显和标题扫光重复。
  计时器继续运行，但图标裁框不含数字。

```text
owner: React（正文 DOM） / controller（scrollTop） / 浏览器（布局与最终像素）
追加正文 → React 提交 → RO 贴底 → 可选残差 translate → paint/composite
                                ↓                         ↓
                         getBoundingClientRect       截图像素/重心
                         两种观测必须分开，不能用前者代替后者
```

## 4. 真实组件消融结果

系统缩放 125%，应用 zoom 100%，正文 22.75px；显示流内源时的八次结果：

| 条件 | 图标 DOM y 范围（CSS px） | 像素重心范围（截图物理 px） | 图标不同像素图样数 |
| --- | ---: | ---: | ---: |
| 原样，显示视觉副本 | 0 | 0 | 1 |
| 隐藏副本，保留 containment + 补偿 | 0.000031 | 0.8668 | 8 |
| 只禁用补偿，保留 containment | 0.7000 | 1.0003 | 2 |
| 只禁用 containment，保留补偿 | 0.000031 | 0.9261 | 8 |
| containment 与补偿同时禁用 | 0.7000 | 0 | 1 |
| 在上一条件上再去掉渐隐 mask | 0.7000 | 0 | 1 |

原始数据：`product-results.json`。同组对照也覆盖 zoom 125% 和 24.5px 行高，结果同向。
图示：`像素对照.png`，直接裁原始 PNG 并以最近邻放大六倍。

扩展验证 `product-confirm-results.json`：系统缩放固定 125%，应用 zoom 100% / 125% /
150%，有效 DPR 分别 1.25 / 1.5625 / 1.875；行高 22.75 / 24 / 24.5px；CSS 动画关闭与开启
两组，共 18 个条件、144 张截图。禁用 containment 与补偿、显示流内源后，每个条件的
八张图标裁片都逐字节相同。各条件之间的不同尺寸不互相比 hash。

细分 containment：最小页中单独 `paint` 能触发约 1px 跳动，单独 layout/style/size 未触发。
但真实组件把 content 改成 `layout style` 仍出现跳动（记录在
`partial-contain-layout-style.log`；该扩展运行超出 55 秒上限，日志保留已完成条件，未算全组通过）。
因此可确认的是**去掉视口 containment 整体有效**；不能把正式方案简化为“只去掉 paint，
保留 layout style 就够了”，也不宣称已解释浏览器内部全部组合行为。

## 5. 旧归因为什么走偏

1. **把 DOM 坐标稳定当作视觉稳定。** 本次同一条件中，DOM 可变化 0.7px 而图标像素完全
   不变；加 translate 后 DOM 几乎不变、图标像素反而变化。这直接反驳“rect 二态就必然抖”。
2. **把副本能治好当作副本必不可少。** 副本绕开原绘制路径，能掩盖问题；并未排除视口
   containment 与补偿本身可以去掉。当前实验明确给出无副本显示也稳定的反例。
3. **Zcode 默认整数行高的前提错误。** 默认实际是 24.5px。不能据此解释两者差异。
4. **RO 在 paint 后交付的断言错误。** rAF 早于当帧布局/RO 的采样可能读到贴底前坐标；
   改成 rAF pin 后 rAF 探针不再报大跳，并不自动证明原先有已绘制的坏帧。`results.json`
   的 timing 记录同一轮 rAF 增高后 RO 校正了坐标；Zcode 源码也利用 RO 绘制前吸底。
   规范入口：[Resize Observer](https://drafts.csswg.org/resize-observer/#algorithms)，
   [HTML rendering](https://html.spec.whatwg.org/multipage/webappapis.html#update-the-rendering)。
5. **量化不是一个固定 0.38px 的神秘常量。** 本机在不同有效 DPR 下观察到不同几何序列，
   24px 行高也可出现 0.32px 二态。桌面交接中的原始环境/数据不齐，本次不冒认复原其 0.38px 来源。
6. **Electron 版本差异不是本次量化的充分解释。** 同一最小页在 Chromium 126 与本机
   Edge Chromium 157 的三档 DPR 下，几何量化结果一致；没有把 Edge 当作 Zcode 实测替身。

## 9. 连续帧复核与跟进修复

连续自然换行、每30ms追加6字符，使用Page.screencastFrame记录合成输出，发现去掉
containment和平移后的真实组件仍可出现1物理像素的二态；两种位置各持续多帧，
不能据此归因为RO晚一帧。原隔离页top=10px恰好稳定，top=48px或48.5px可复发。
先前矩阵只改变缩放和行高、固定视口起点，是覆盖缺口。

本次实读Zcode运行窗口：3.18.2，Electron44.7.0 / Chromium152.0.7977.130，DPR1.25，
UI字号14px；活动timeline及七层祖先的contain/transform均为none。开发者工具已关闭。
原生inline-flex、单独取消动效/content-visibility/mask、增加合成层、相对top补偿、
同SVG背景图、sticky均没有在Electron31跨所测起点消除跳动；未确认Zcode实际流式图标
在全部起点的逐像素行为，不再将局部CSS差异宣称为两产品差异的充分解释。

跟进小修采用单节点定位：MessageScrollerPinnedRow始终包含同一份工作行和读屏文本。
短内容/reading按正常流排版；overflow且following时，外层保留实际高度，内层同一节点
用fixed定位到viewport.bottom减去内容尾距。继承原主题，无portal、无副本、无每帧轮询。
RO只同步尺寸/位置，不写scrollTop；跟随意图订阅在上滚capture同栈解除定位。

```text
owner: controller（following与scrollTop），PinnedRow（同一节点的定位与占位）
内容尺寸变化 → controller按following贴底；PinnedRow按viewport/尾距定位
上滚capture → following=false → 同栈恢复流内定位
主动回底 → following=true → 溢出时启用定位
终态/卸载 → 移除唯一工作行、清RO与订阅
```

验证必须覆盖不同视口起点、Windows等效DPI 1/1.25/1.5、连续帧，以及阅读/回底/缩回短内容、
后置提示、停止、节点替换。实验日志位于continuous-*.json；新的实现仍需用户最终复验。
