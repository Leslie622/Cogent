## 0. 背景：为什么动这一刀

工具循环落地后一次 run = 多段 assistant（思考段 / 工具卡 / 中间正文 / 终答），
现状是**平铺**：每段一行、各自带用量行，过程与结果没有层级 —— 用户观感"很乱"
（实测截图：两个用量行 + 平级的过程项 + 思考块孤悬）。主流共识 = **过程两态**：

- 进行中：摊开直播（用户盯着看进度）；
- 完成后：整体收进一条可展开的轨迹摘要，只留终答正文（结果才是要读的）。

## 1. ZCode 模式解构（对齐目标）

进行中（live）：

```
用户气泡
过程体（自动展开，逐步出现：思考块流式 / 工具卡执行中 / 中间正文）
[输出位置] 工作中（spinner + 计时，常驻 —— 过程间隙的唯一活动信号）
```

完成（done）：

```
用户气泡
已工作 1.2s ⌄        ← 头条（点击开合过程体；终答常驻其下）
├（展开时）已深度思考
├（展开时）read(路径) 完成
├（展开时）中间正文段（带自己的用量小字）
终答正文（常驻，不折叠）
↑ 合计 · ↓ 合计 · 缓存读 · ≈$（回合聚合一条）
```

## 2. 已定决策（评审后不再翻烧饼）

| # | 决策 | 理由 |
| --- | --- | --- |
| D1 | 回合分组 = **渲染期**按相邻关系（用户消息 → 下一用户消息为一个回合），store 数据模型不动（平铺保留） | 分组是纯呈现关切；协议 / store 零改动，事件流逻辑不重写 |
| D2 | 终态结构 = 头条（已工作 Xs，开合过程体）+ 过程体（思考 / 工具 / 中间正文，默认收起）+ 终答正文（常驻）+ 回合聚合用量行 | ZCode 同款；"过程（灰、可折叠）→ 结果（黑、常驻）"的视觉层级 |
| D3 | 进行中 = 过程体摊开直播 + 底部「工作中」常驻行（spinner + 计时）；**终答开流即折叠**（2026-11-10 用户定调：结果出来了就直接把过程收进 live 态头条「工作中 ⌄」，不等 run 终态事件；若正文后又来工具调用则回到直播态重新摊开） | 用户点名的两条：输出的位置一直显示工作中 / 上方是流程；折叠时机以"结果开始出现"为准，而非"结果全部输出完" |
| D4 | 开合语义 = `open ?? 默认`（用户手动优先）：stopped 默认展开（半截正文别藏）、done / failed 默认收起；终态到达自动收起（用户没动过时） | 与 Reasoning 件的 `open ?? running` 同款语义，家族一致 |
| D5 | 回合时长 = **墙钟**（提问 timestamp → 回合末条内容消息 timestamp），不用各段 durationMs 求和（不含工具执行耗时，会虚低） | "已工作"语义 = 用户等了多久；两头数据都有（含历史回查），协议零新增 |
| D5′ | D5 修订（2026-11-10 首验翻车）：pi 的 assistant `timestamp` = **流打开时刻**（pi-ai 各方言 stream open 构造 partial 时打点）——直接沿用则「已工作」漏掉末轮整个流式输出段（实测 live 计时 2.7s、终态报 1.4s）。修法：session.ts turn_end 覆写 `event.message.timestamp = Date.now()`（轮结束时刻），**连消息体一起改**（该对象即持久转录真源，不改历史回查退回轮开始口径；轮已收尾 pi 不再读该字段） | 时刻单一来源（turn_end 的墙钟），fresh 段/持久转录/历史投影三口径同源 |
| D6 | 终态四态 = 工作中 / 已工作 Xs / **已停止**（abort：半截正文封存保留 + 清错误条）/ **出错了**（真失败：错误条照旧）；abort 封存 = 流式占位改名 `live-*`（同 tool.started 的封段接力），不再移除 | 承接工具计划批次 3 的「已停止」占位；中止不是错误，红条 + 占位双份是噪音 |
| D7 | 用量聚合 = 回合内各段求和只显示一条（终答下方）；过程体展开时各中间段保留自己的用量小字。**时长双口径并存（2026-11-11 修订）**：头条墙钟（用户等了多久）+ 统计行接口时长（各段 durationMs 求和 = 模型净耗时，不含排队/引擎处理），两个数语义不同不算重复。**带工具回合再分解（同日追加）**：`5.7s 模型 · 1.4s 工具` —— 工具时长 = 各工具起止区间的**并集**（pi 并行执行同批工具，逐个相加会按 CPU 口径重复计墙钟），起止来自引擎事件打点（流式）/ toolResult 的 timestamp−durationMs（历史回查，转录原生字段，重启不漂移） | 默认视图干净（主流形态），展开仍有逐段透明度（学习项目取向）；原"时长不重复记"被用户推翻 —— 接口时长与墙钟是两个正交信息，都值得显示；模型+工具 ≈ 墙钟（残差 = 引擎开销毫秒级），三数自洽可对账 |
| D8 | 无过程回合（单段纯文本、无思考无工具）也**恒挂「已工作 Xs」头条**（过程体为空 → 不可展开单行）。**2026-11-11 修订**：原案"纯文本直出不挂条"作废 | 原案借 ChatGPT 规则，与本计划自己的北极星（ZCode 形态）矛盾 —— 用户实测 ZCode：无思考无工具的问候也显示"已工作 4 秒"。慢本身是信号；且首句若撞上引擎冷启动（方言模块懒加载秒级），计时器数到 5s 后整行消失的观感是 bug 级 |

## 4. 边界与风险

| 风险 | 对策 |
| --- | --- |
| scroller 库按 content 直接子元素测项数/高度 | 回合包 div 后：吸底跟随走 ResizeObserver 路径、scrollToMessage 走注册表、刻度走全视口 DOM 查询（均已核对源码） |
| 终答段之后还有工具项（模型末轮只调工具没收尾） | 切分规则 = 末条**有正文**段为终答，其后项留过程体（顺序小让步，代码注释说明） |
| stopped / failed 只在活动会话末回合可辨（flags 会话级，不随回合持久化） | 下一回合开启后旧回合头条回落"已工作 Xs"；失败详情仍由底部错误条承担（v1 可接受） |
| 中止 raced 完成（abort 后 run.completed 先到） | run.completed / run.failed 都清 stopping 位 |
| 计时器每秒重渲染 | 工作中行自持 state，只重渲染自己一行 |
| 过程体折叠时消息条目卸载（scroller 注册表删项） | 唯一定位调用方（索引刻度）只锚用户消息，恒挂载 |

## 5. 明示不做（防摊大饼）

批次间消息时间线（工具执行耗时段可视化）、过程项逐个折叠态持久化、
ChatGPT 式"思考原文不留"（我们保留 —— 数据已到客户端，藏了没意义）、
消息级 hover 工具栏（复制/点赞，ZCode 截图有，属后续件）、多 run 回合
（一次提交恒一个 run，引擎已保证串行）。

## 6. 验收清单（Done 的定义）

1. 发消息 → 回复位立即「工作中」（spinner + 计时），过程（思考 / 工具）在其上方
   逐步直播；
2. 完成 → 上方「已工作 Xs」一条，默认收起；点开复盘全过程（思考 / 工具 / 中间
   正文 + 逐段用量小字）；
3. 终答正文常驻头条之下，用量聚合成一条（↑↓ 缓存 成本 合计）；
4. 中止 → 头条「已停止」、半截正文保留、无错误红条；真失败 → 头条「出错了」+
   底部错误条；
5. 纯文本回答（无思考无工具）也挂「已工作 Xs」单行头条（不可展开，D8 修订）；
6. 重启 / 切会话回查：结构同构（分组靠相邻关系，时长靠 timestamp 差）；
7. 三关全绿。

> **追加修订（2026-11-11，批次 A 首验收）**：用户首验发现两处呈现分歧，根因同链：
> 1. **首句墙钟 5s vs 统计行 1.2s** —— pi 的 API 方言模块是首次请求时动态
>    import（lazyApi），冷启动拉起 openai SDK（26MB，Windows Defender 扫描放大）
>    实测 3.8s，全落在首条消息上；而 durationMs 只计方言流对象创建→结束
>    （接口净耗时，auth/懒加载不计）。修法 = 引擎启动即后台预热三方言
>    （agent-service/index.ts；与懒加载命中同一模块缓存 —— exports 子路径与
>    lazy 相对 import 解析到同一文件 URL）；durationMs 口径保持，用户定调
>    墙钟/接口时长**双口径并存显示**（D7 修订，聚合行补 ΣdurationMs）。
> 2. **纯文本回合计时器消失** —— D8 原案（不挂条）被用户以 ZCode 实测推翻
>    （无思考无工具的问候也显示"已工作 4 秒"），修订为恒挂头条、空过程体
>    不可展开（RunTrace 无 children 时退化为单行）。
> 3. **「工作中」计时器冻住**（同日二验，两轮排查定论）：组件逻辑、主线程
>    饱和（30ms delta 洪水下照常走秒）、窗口节流（失焦也走秒）逐一实证排除
>    后，真因是**跳字粒度** —— Elapsed 原为 1s 一跳，首跳在 +1s，而预热落地
>    后快回合（问候语 ~1s 跑完）全程只剩挂载零头「6ms」死数字，观感即秒表
>    停走。修法 = interval 1000→100ms（码表式滚动）。同轮加固（非根因）：
>    两窗口 `backgroundThrottling: false`（VS Code 同款）+ Elapsed 挂
>    focus/visibilitychange 即时对齐。排障手法（原 开发.md 已删）：真应用内 dev-only
>    强制直播态 + ELECTRON_ENABLE_LOGGING 分层日志（interval/DOM/事件时序）。
> 4. **墙钟 7.1s vs 聚合行 5.7s 对不上账**（同日三验，带工具回合）：差额 1.37s
>    全是工具执行（glob 802ms 串行 + 551ms 三连并行）—— 双口径只覆盖了
>    「墙钟/模型」，工具段成了账外黑洞。落地 D7 追加项：聚合行分解
>    「Xs 模型 · Ys 工具」，工具 = 起止区间并集（协议 ToolCallRecord 扩
>    startedAt/endedAt，只增 optional；历史回查自 toolResult 原生字段重建）。
>    HomeChat 的 dev 探针（修订 3 遗留）定位后待删。
