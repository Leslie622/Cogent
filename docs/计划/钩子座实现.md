## 1. 目标与动机

全局架构 D7：钩子座 = InlineExtension（审批拦截 / 审计 / 上下文注入 / 系统提示节）。
现状三类干预散在三处、三种形状：

| 干预 | 现挂点 | 形状 | 现状评价 |
| --- | --- | --- | --- |
| 系统提示段 | factory 匿名工厂 `pi.on('before_agent_start')`（pi-session-factory.ts:217-231） | 扩展事件 ✅ | 机制对，但匿名、无座籍 |
| 审批拦截 | 链式包裹 `session.agent.beforeToolCall`（factory:270-280 → session.decideApproval） | 官方钩子链包裹 | **signal 语义已对齐 zcode/dsh**（见 §2.4），保留 |
| 观测/审计 | inspector 走 AgentOptions 三回调（session.ts:1539+）+ translateEvent 旁路 | 官方观测口 | 厂商标量真源，保留（§3.3 不迁的理由） |

本批两件事：
1. **装配统一**：四类干预收进一个具名钩子座文件，三角色（接口/实现/消费）落位可对账（dsh 纪律的文档级轻量版，不建 CI 机制 —— Cogent 钩子消费者全是 Host 内部，无第三方生态）；
2. **审批审计对**：`approval.asked` / `approval.decided` 成对进 inspect 观测流（现状审批往返零观测记录，放行无痕、跨重启不可回看 —— dsh「放行也留痕」纪律）。

## 2. 对比结论（三仓 + Pi-meme，出处：文件:行号）

### 2.1 pi：signal 缺陷两个版本都在，链式包裹必须保留

- loop 层已传 signal：`reference/pi/packages/agent/src/agent-loop.ts:745`
  （`config.beforeToolCall(context, signal)`）—— Cogent 包裹层拿得到 signal 的原因；
- AgentSession 适配器丢 signal：installed 1.5.2 dist `agent-session.js:377` 与
  reference HEAD（827383a15）`core/agent-session.ts:716` 均为
  `(context) => this._beforeToolCall(context)` 单参 —— **扩展 `tool_call` 事件至今
  看不到 signal**；
- 锚点后唯一相关提交 `4438c58ba`（fix: answer every tool call when a batch is
  aborted）只修「未执行调用无结果」：hook 前后各查一次 `signal.aborted`
  （agent-loop.ts:718,747）。但挂起中永不 resolve 的钩子（审批场景）在 747 行
  检查执行不到 —— 永悬问题原样在。**结论：审批不能搬进 `tool_call` 扩展事件，
  链式包裹在 1.5.2 与 HEAD 都必要**（升级 pi 版本时重查此项）。
- 扩展事件面：1.5.2 与 HEAD 一致（32 事件，`core/extensions/types.ts:1426-1458`）。
  四用途对应官方缝：系统提示段 `before_agent_start`→`systemPromptOptions.sections`；
  上下文注入 `context`（types.ts:899-909，每次 LLM 调用前可改 messages）；
  审批 `tool_call`（block/terminate，缺 signal 见上）；厂商标量
  `before_provider_request{payload}` / `after_provider_response{status,headers}`
  / `provider_stream_event{provider,api,model,data}`（types.ts:921-951）。

### 2.2 Pi-meme：单工厂集中装配的形状先例

`packages/pi-runtime/src/sdk/session.ts:570-795`：一个内联工厂集中注册全部
`pi.on(...)`（context 门控、目标限流、sections、model 同步）。钩子座取同款形状
（具名版本），不学它把审批也塞进事件（它没有审批挂起语义要保）。

### 2.3 dsh：决策词汇 + 审计配对，两条纪律进来

- 审计配对（本批采）：`approval/asked` + `approval/decided` 同 id 成对落会话
  事件流、被 turn 边界包围、**审计写不进去就拒绝返回决策**（fail-closed）——
  `interaction/user-approval/src/index.ts:225-251`、`types.ts:34-59`；
- 决策词汇 + 单调 guard（不采，真实的墙：Cogent 无第三方钩子生态，guard 层
  防的「监听器顺序翻案」不存在）：`core/tools/src/contracts.ts:375-409`；
- signal 是事件 payload 一等字段（已等效达成）：`user-approval/src/index.ts:320-333`
  「挂起请求与 signal abort 竞速、迟到答案构造性丢弃」—— 与 Cogent
  session.ts:1290-1295 现有实现同构。

### 2.4 zcode：signal 全链路 + 放行也留痕

- signal 全链路显式：turn 级 scope → executor → broker 挂起 Promise，abort 折
  `ToolCancelled` 且挂起审批仍发终态事件 —— `permission-request.ts:21-47`、
  `permission-flow.ts:338-358`。Cogent 对应物已齐（abort listener 兜底 resolve +
  工具错误结果进 pi 树），**无需改动**；
- 「放行也留痕」：每次判定 `tool.permission.evaluated` 结构化日志 +
  `PermissionRequested/Resolved` 事件 —— `permission-flow.ts:199-218`。Cogent
  缺口正是这个：审批往返不进 inspect 流。本批补。

## 3. 设计

### 3.1 装配形状（owner + 事件顺序）

新文件 `src/host/runtime/hook-seat.ts`：具名 InlineExtension 工厂 + 审批包裹器
集中地。factory 的 extensionFactories 从「匿名 sections 工厂 + MCP 工厂」变为
「**cogent-hooks 工厂** + MCP 工厂」。

```
owner: 钩子注册表 = hook-seat.ts（唯一新增文件，三角色对账表见模块页）
owner: 审批挂起表 = session.ts（pendingApprovals，不变）
owner: 观测流 = inspector.ts（不变，新增审批两类条目）

装配期（buildPiSession，每会话一次）:
  extensionFactories ← [ createCogentHooks({sections}), mcp?... ]
      └ pi.on('before_agent_start')  ← sections 段表（从 factory 匿名工厂迁入，逻辑零改动）
  session.agent.beforeToolCall 包裹 ← hook-seat 导出的 wrapApproval(piBefore, approval)
      （留在 factory 调用点；它绕开扩展分发器是补丁不是扩展 —— 注释钉死原因）
  AgentOptions 三观测钩 ← session.attachInspector（不变，§3.3）

运行期（一次写工具调用）:
  loop ─beforeToolCall(ctx, signal)→ 包裹层 ─decide→
    read/auto/规则放行 ─→ inspector 记 approval.decided(allow 类) ─→ 委托原链
    ask ─→ 记 approval.asked ─→ notify('approval.request') ─→ 挂起
      ↙ respond(用户)                      ↘ signal abort(停止钮)
    记 approval.decided(裁决词) ←── 先到先得，败路构造性丢弃（现状语义不变）
```

### 3.2 审批审计对（协议 additive，PROTOCOL_VERSION 不动）

- `InspectEntryKind` 加 `'approvalAsked' | 'approvalDecided'`（additive：旧消费者
  未知 kind 按现有未知值兜底路径走，只增不破）；
- asked 条目：requestId / toolName / kind / summary / outsideRoots / 档位快照；
- decided 条目：requestId / 裁决词（`allow` / `deny` / `always-workspace` /
  `aborted` / `settled`）/ reason；
- 覆盖**全路径**：decideApproval 的每个 return 分支都过一次记录点（放行/计划
  拦截/ask 挂起三路 + respond/abort/settle 三收尾）—— zcode「放行也留痕」口径；
- 控制台 `kinds.ts` 加两 kind 呈现映射（对齐现有条目风格）；
- 尽力观测语义不变：记录失败不炸对话（inspector 现有纪律）。

### 3.3 厂商标量观测不迁扩展总线（真实的墙）

AgentOptions 三回调保留为厂商标量真源，不迁 `before_provider_request` 等事件：
- 载荷不等价：`onPayload(payload, model)` 带 model 上下文，事件版只有
  `payload`（types.ts:921-925）；onResponse 同；迁移有丢模型上下文的真实风险；
- 现路径是官方口（「pi 原生观测口子，零魔改」），不是绕官方；
- 收益盘点：迁移唯一收益是「形状统一」本身 —— 为形状冒数据保真风险，不划算。
  钩子座的「审计」成员 = inspector 现状 + 本批审批对，厂商标量三钩在模块页
  挂「观测口（非扩展）」籍。

### 3.4 上下文注入（`context` 事件）：预留缝，首发不做

真实的墙：pi 每次 prompt 自动追加 `<cwd>` 环境段（factory 注释实证，重复声明
无害已对账），Cogent 工作区注入走系统提示段（session.ts:187 装配）——
`context` 事件当前**无未满足的消费者**，为缝而缝无功能收益。座内留位：hook-seat
导出的工厂签名带 `context?: (messages) => AgentMessage[] | void` 可选注入位，
有真实需求时接线（写明触发条件：出现「需要按调用注入动态事实且系统提示段
不适合」的场景）。

## 4. 边界 / 首发不做（逐条真实墙）

1. 审批不搬进 `tool_call` 扩展事件 —— pi 分发器丢 signal（1.5.2 与 HEAD 均在，
   §2.1），搬 = 挂起审批遇停止永悬；
2. 不建 dsh 式 CI 级三角色守卫 / 事件目录生成 —— Cogent 钩子消费者全是 Host
   内部、无第三方生态，守卫防的腐化模式不存在；模块页文档级对账表即可；
3. 不建 zcode 式 matcher/timeout/进程级 hook 配置 —— 同上，无外部 hook 来源；
4. 厂商标量观测不迁事件总线 —— §3.3 载荷不等价；
5. `context` 注入缝不接线 —— §3.4 无消费者；
6. 审批无超时维持 D5 定稿（用户不点就一直等，停止钮可 abort）—— 不引入
   zcode timeoutMs / dsh timeout-policy。
