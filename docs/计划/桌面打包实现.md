# 桌面打包实现 — 工程化打包方案（Windows & Linux `.deb`）

> 状态：已实施 Windows 打包与双平台工程化管线（Windows NSIS + 隔离冒烟已实测通过；Linux `.deb` 管线与 CI 已就位，因本机未装 WSL 分发版暂未现场生成 `.deb`）。
> 关联基准：[架构](../架构.md#构建与运行时)、[全局架构](全局架构.md#2-平台边界与理由)、[决定 31](../决定.md#架构级取舍)、[Node运行时分发](../技术笔记/Node运行时分发.md)。

## 1. 目标

围绕以下三项核心要求，在不引入内置 Python 的前提下建立工程化桌面打包体系：

1. **单命令、单文件配置**：只维护一份打包配置文件（`packaging/pack.config.json`），日常只执行一条命令（`npm run pack`）即可完成全部目标出包。
2. **分项目组独立出包**：在同一配置内按项目组定义各自独立的 `id`（`appId`）、`name`（显示名/产品名/进程与包标识）、`version`、`icon` 目录及可选安装/数据目录参数；切换项目组或批量出包不污染仓库根目录 `package.json`。
3. **严格控制出包体积（不该带的绝不带）**：通过白名单依赖闭包收口 + 平台原生文件裁剪 + `afterPack` 门禁，剔除已被 Vite 打包进 `out/renderer/` 的巨型 UI 依赖、开发依赖与异平台二进制。
4. **双平台覆盖与产物可用性校验**：产出 **Windows（NSIS / Portable）** 与 **Linux `.deb`（`x64` / `arm64`）**，支持 Windows 宿主机下直接本机打 Windows 包 + 自动经 WSL 原生磁盘打 `.deb`（Linux 宿主机 / CI 则原生直打），并用冷启动冒烟验证打包态可用。

## 3. 整体方案设计

### 3.1 单文件配置 + 分项目组结构

所有打包参数、目标矩阵、镜像源与各项目组差异集中写入**唯一配置文件** `packaging/pack.config.json`；图标目录按项目组存放在 `packaging/icons/<projectKey>/` 下（由配置中的 `iconDir` 显式指定）。

```text
packaging/
├─ pack.config.json              # 唯一配置文件（全局开关 + 各项目组定义）
├─ build.mjs                     # 单命令编排入口（npm run pack）
├─ config-schema.mjs             # Zod 校验与默认值解析
├─ runtime-closure.mjs           # 依赖闭包提取、体积裁剪与 afterPack 审计
├─ smoke-packaged.mjs            # 产物隔离冷启动冒烟
└─ icons/
   └─ cogent/                    # 默认项目组图标集（各项目组自建目录即可）
      ├─ icon.ico                # Windows EXE / NSIS / 托盘
      ├─ icon.png                # 512x512 通用源图
      ├─ tray.png                # Linux 托盘图（16/32/64px）
      └─ linux/                  # 16x16.png ... 512x512.png（hicolor 标准尺寸）
```

### 3.2 打包产物布局与品牌注入

```text
<安装根目录>/
├─ <name>.exe / <executableName>       # Electron 40.9.3 主程序
└─ resources/
   ├─ app.asar                         # package.json（含 extraMetadata）、out/preload/**、out/renderer/**
   ├─ app.asar.unpacked/               # 独立 Node 22 直读区
   │  ├─ out/main/                     # index.js、host.js、mcp.js、4 个 worker、chunks/*
   │  └─ node_modules/                 # 仅白名单闭包内的运行时依赖（无前端 UI 库与 devDeps）
   ├─ runtime/<win-x64|linux-x64|linux-arm64>/
   │  ├─ bin/node(.exe)                # 官方 Node 22.23.5（SHA256 校验）
   │  ├─ LICENSE
   │  └─ runtime.json
   └─ icons/                           # tray.ico / tray.png / icon.png
```

为让分项目组的 `name`、`id`、`icon` 与可选 `storageDirName` 真正在应用内生效（而非只改安装器外壳），实施时做三处极小且内聚的源码接线：

1. **构建期品牌常量注入（`electron.vite.config.ts`）**：支持从环境注入 `__COGENT_APP_NAME__`（默认 `'Cogent'`）与 `__COGENT_STORAGE_DIR_NAME__`（默认 `'.cogent'`），替换 `index.html` `<title>`、`HomeSidebar.tsx`、`CloseAskDialog.tsx`、`console.ts`、`embedded.ts` 的写死展示名；Electron 主窗口与托盘在运行期读取 `app.getName()`（由 `electron-builder` `extraMetadata.productName` 写入）。
2. **主进程入口与图标解析（`src/electron/main/app-paths.ts`）**：
   - `resolveUnpackedMainEntry(file)`：`app.isPackaged ? join(process.resourcesPath, 'app.asar.unpacked', 'out', 'main', file) : join(import.meta.dirname, file)`，用于 [index.ts:187](../../src/electron/main/index.ts#L187) 启动 `host.js`。
   - `resolveTrayIconPath()`：Windows 优先取 `resources/icons/tray.ico`（回退 `app.getFileIcon`），Linux 读取 `resources/icons/tray.png`（解决 Linux ELF 无内嵌图标导致托盘空白的问题）。
3. **跨平台运行时下载（`scripts/fetch-runtime.mjs`）**：增加 `--platform <win32|linux> --arch <x64|arm64>` 参数，使单条 `npm run pack` 能一次性把 `win-x64`、`linux-x64`、`linux-arm64` 的 Node 22.23.5 备齐并核验 SHA256。

### 3.3 体积控制流水线（“不该带的绝不带”）

1. **只打入必要 `out/` 与最小运行时 `node_modules` 闭包**：
   - 预生成临时舞台清单或使用 `electron-builder` `files` + `asarUnpack` 精确白名单，**禁止使用 `node_modules/**/*` 全量复制**。
   - `runtime-closure.mjs` 扫描 `out/main/**/*.js` 所有非内置外部导入（`import` / `import.meta.resolve` / `createRequire().resolve`），递归收集其 `dependencies`（及未在 `excludeOptionalDeps` 黑名单里的 `optionalDependencies`），得出精确包清单；对不在该清单内的全部 `node_modules`（`react`、`mermaid`、`@lobehub/icons`、`@pierre/diffs`、`katex`、`vitest`、`eslint`、`typescript`、`patch-package`、`@napi-rs/canvas*` 等）一律不进包。
2. **按目标平台/架构二次裁剪**：
   - 去除 `**/*.map`、`*.pdb`、`**/*.d.ts`（注：仅在运行时无 `jiti`/TS 类型加载依赖时或白名单豁免）、`**/test/**`、`**/tests/**`、`**/__tests__/**`、`**/README*`、`**/CHANGELOG*`、`**/docs/**`。
   - `@earendil-works/pi-tui/native/` 仅保留当前目标 `<platform>-<arch>` 目录（移除另外 5 套平台的 `.node`）。
   - `resources/runtime/` 仅将当前目标对应的单一平台目录打入该目标包（Windows x64 包只带 `win-x64`，Linux arm64 `.deb` 只带 `linux-arm64`）。
   - `electronLanguages` 仅保留 `["en-US", "zh-CN"]`，删去其余数十份 Chromium `.pak` 语言包。
3. **WSL 打包优化（Windows 一键打 `.deb`）**：
   - 不向 WSL 同步本地 `1.35 GB` 的 `node_modules`：在 Windows 本机先用 `runtime-closure.mjs` 将**唯一必需的运行时闭包**整理到隔离暂存区 `.pack-staging/node_modules`（并剔除非 Linux 原生文件），再将 `out/`、`package.json`（只读副本）、`.pack-staging/node_modules`、`resources/runtime/linux-*`、对应项目组 `icons/` 经 `rsync --delete` 同步到 `wsl.workspace` 并校验 MD5 与 `linux-arm64/x64` ELF 魔数；WSL 内维护独立 `wsl.builderCacheDir` 安装一份 Linux 版 `electron-builder` 执行打包，最后把 `.deb`（及校验文件）回拷到 `dist/<项目组>/`。

### 3.4 单命令执行时序

```text
npm run pack（读取 packaging/pack.config.json）
  ├─ 1. Zod 校验配置 + 检查每个待打包项目组的 iconDir 必需文件（.ico / 512.png / linux 多尺寸）
  ├─ 2. 按目标平台调用 fetch-runtime.mjs 准备并验证 Node 22.23.5（runtime.json + SHA256）
  └─ 按 active 项目组循环（每个项目组隔离输出到 dist/<projectKey>/）：
        ├─ 3. 带项目组品牌变量执行 electron-vite build → 产出 out/
        ├─ 4. runtime-closure.mjs 扫描 out/main/**/*.js → 生成精确闭包并校验无未登记外部包
        ├─ 5. 若启用 windows：调用 electron-builder API（内存配置，不改根 package.json）产出 NSIS/Portable + afterPack 审计
        ├─ 6. 若启用 linux deb：
        │     ├─ Linux 宿主机：直接调用 electron-builder API 打指定 arch 的 .deb + afterPack 审计
        │     └─ Windows 宿主机（wsl.enabled=true）：rsync 精简工作区至 WSL → MD5/ELF 校验 → WSL 打各 arch .deb → 回拷 dist/<projectKey>/
        └─ 7. 生成 dist/<projectKey>/package-manifest.json 与 .sha256（含包体积、Git 提交、各目标摘要）
```

## 4. 边界、排除项与风险

1. **内置 Python（延后）**：本批不随包分发 Python（符合决定 31 与当前指示）；配置结构预留 `extraResources` 扩展槽位，后续接入无需推翻本流水线。
2. **预置 `fd` / `rg`（延续现状）**：继续由 `pi` 按需下载至 `<COGENT_HOME>/pi/bin` 或读取系统 `PATH`（见 [工具系统](../模块/工具系统.md#外部二进制依赖fd--rg部署事实)），不阻塞首版安装包。
3. **代码签名与在线自动更新**：保留签名钩子与 `package-manifest.json` 输出位，无证书环境下产出未签名安装包并在 manifest 标注 `signed: false`；不绑定在线更新服务端。
4. **Windows 下生成 `.deb` 的环境前提**：依赖本机启用了 WSL2（内部有 `node`、`rsync`、`fpm`/`dpkg`/`xz` 等 `.deb` 工具链）；若宿主机既不是 Linux 也没有可用 WSL，脚本会在第 1 步预检明确报错并指引改用 Linux CI（`.github/workflows/package.yml`）或安装 WSL。
5. **项目组数据隔离选择**：不同项目组默认共用 `~/.cogent` 还是各自独立目录（如 `~/.sxz`），由项目组配置中的 `storageDirName` 控制，避免不同项目组桌面应用混写同一会话与凭据文件；若未填则默认 `.cogent`。

## 5. 验收标准

1. **工程四关通过**：`npm run lint && npm run typecheck && npm run build && npm test` 全绿，新增打包脚本、Schema 校验、闭包收口、品牌注入与 `app-paths`/`window-close` 改动均附带单测。
2. **单命令、单配置验证**：仅编辑 `packaging/pack.config.json` 增加第二个测试项目组（不同 `id`/`name`/`iconDir`），只跑一次 `npm run pack`，根 `package.json` 与 `git status` 无脏改动，且 `dist/<projectKey>/` 下分别产出对应名字、图标与独立 `appId` 的安装包。
