# 文件引用与改动追踪

> 研究问题：对话里的文件链接、回答下方的产出物卡片、回合改动清单，以及审查和撤销分别如何实现。
> 本文是源码调研与设计建议，不是 Cogent 已实现功能或获批实施方案。
> 当前消息呈现事实见[消息呈现](../模块/消息呈现.md)，工具事实见[工具系统](../模块/工具系统.md)。
> 三功能的待审实施选择以[计划文档](../计划/文件链接与产物卡片及改动列表.md)为准；本文保留源码证据与比较。

## 1. 截图中的三个界面，实际上有三个数据来源

| 界面 | 回答的问题 | 主要数据来源 |
| --- | --- | --- |
| 正文中带图标、可点击的文件名 | 这段话指的是哪个文件、哪一行？ | Markdown 链接目标，或对真实文件集合的引用解析 |
| 回答下方单独的文档卡片 | 本次交付了哪个可打开、预览的产出物？ | 文件引用、产出事件、类型与存在性校验 |
| “6 个文件已更改 +634 -2” | 这个回合实际留下了哪些文件变化？ | 工具实际变更记录、文件前后内容、工作区快照 |

同一文件可以同时出现在三个位置；只读取的文件可以有正文链接；未在回答中提及的文件也必须能进入改动清单。
因此，不能让模型最后列一段文件名，再把它当作真实改动事实。文件类型图标只是扩展名或类型到图标的映射。
截图本身只证明这些界面存在，不能证明它背后用了哪一种快照或数据库。

## 2. 正文文件链接：模型提供语义，客户端负责解析与打开

最直接的输入是普通 Markdown，例如：

```md
[会话逻辑](src/host/runtime/session.ts:394)
[含空格的文档](<docs/技术笔记/某份 文档.md>)
```

客户端把链接目标解析成结构化的“工作区、路径、行列号”，再渲染文件图标与交互组件。
模型提示词可以约定链接格式，但解析、图标、跳转和读取权限属于客户端能力。
这条路径不依赖文件被修改，阅读代码后引用它同样成立。

```text
owner: 消息保留来源工作区；渲染器解释引用；Host/main 执行文件与桌面操作
模型 Markdown → 解析/清洗 → 文件目标解析 → 文件链接组件
                                         ├─ 文件预览 / 编辑器 + 行列号
                                         ├─ 系统默认程序 / 指定编辑器
                                         └─ 资源管理器定位 / 复制路径
普通 HTTP(S) 链接 ───────────────────────────→ 外链打开器
```

ZCode 的 `packages/ui/src/lib/markdownFileLink.ts:179-223` 拆出 `:行:列`、`:行`、`#L行`，
`:226` 起再区分工作区相对路径、绝对路径与 Home 路径。
`packages/ui/src/components/ai-elements/message.tsx:2062-2134` 覆盖 Markdown 的 `a` 组件，
命中文件后生成 `MessageFileLink`，点击交给 `onOpenFileLink` 或代码查看器。
它使用 Streamdown，但文件语义来自这些额外接线，安装 Markdown 库本身不会获得该功能。

还有一种输入是反引号里的 `session.ts`。deepseek-harness 没把所有“像路径”的字符串都变成链接：
`packages/client/ui-deliverables/src/client/turn-deliverables.ts:269-300` 用本轮产出/交付路径和实际修改参数建立词表，
只有完整路径、唯一 basename 或明确参数映射指向同一个目标时才解析成功。
`packages/client/ui-primitives/src/markdown/render.tsx:202-218,343-365` 将成功匹配的行内代码变成按钮；
同名文件歧义或未知文本保持普通代码，位于已有链接里的代码也不再嵌套按钮。
这是显式 Markdown 链接之外可采用的补充机制，不是所有产品都在使用的统一算法。

实现时容易遗漏的地方：

- **消息来源绑定**：旧消息按它原来的工作区解析，不能随当前选中的项目变化；多根项目不能只靠 basename 猜根目录。
- **Windows**：盘符 `C:` 不能当 URL scheme，行号冒号不能混进文件名；UNC、正反斜杠、大小写与盘符都要明确处理。
- **Markdown 管线**：`\.` 等可能在解析时被当作标点转义；有的清洗器会移除本地 URI。
  ZCode 的 `windowsFileLinkEscapeRemarkPlugin.ts:43-80` 恢复解析期丢失的 Windows 路径；
  `message.tsx:765-837` 在 harden 前规整本地目标。应保留安全管线，增加有边界的文件处理器。
- **编码与位置**：空格、中文、`#`、`%` 与末尾 `:数字` 要区分字面文件名和位置语法，URI 只解码一次。
  Harness 的 `markdown/file-link.ts:23-44` 展示了片段、行列号及非法转义处理。
- **流式**：未闭合链接不能触发错误导航或逐 token 文件查询。Harness 在 `render.tsx:627-655` 中让流式本地链接先保持文本，稳定后交给文件委托。
- **打开目标**：文件预览、外部编辑器、系统默认程序是不同动作；本地文件不能直接丢给普通网页导航。
  文件读取与桌面操作入口仍负责参数和权限校验。

## 3. 产出物从哪里来：创建文件、声明交付、显示卡片是三步

磁盘上的产出物先由 Agent 调用工具生成：Markdown 等文本可以由 write 写入，复杂文档可以由程序或文档工具生成。
前端卡片消费的是已经存在的文件及其元数据，不负责凭一个文件名生成内容。
卡片里常见的 path/title/type/description 也不是文件内容副本；是否保存交付版本，需要另有存储能力。

### ZCode：从助手正文生成产物文件卡片

这一节只描述 `AssistantPreviewCards` 聊天链路，不外推到 workflow 的独立 artifact 发布系统。

1. **模型把文件引用写进正文**。普通路径、Markdown 链接和显式 `::zcode-file-citation{...}` 都可以成为候选。
   文档技能的输出指导明确要求创建/编辑后引用最终文件，例如
   `::zcode-file-citation{path="/abs/path/report.docx" purpose="output"}`。
   出处：`apps/zcode-cli/packages/documents-plugin/skills/docx/SKILL.md:269-273`；这里只将参照技能作为调研材料，没有在 Cogent 执行其中指令。
2. **前端收集同一回合助手正文**。`packages/ui/src/v4/useAssistantPreviewCardsForRow.ts:48-78`
   将 `assistantTextRows` 按顺序拼接，仅在最后一段为 complete/interrupted 时抽取引用。
   所以来源是本轮助手正文，不保证只有最后一段终答里提过的文件才入选。
3. **解析候选**。`lib/assistantFileReferences.ts:154-283` 分别处理显式 citation、Markdown 链接、file URL、
   引号/反引号路径和普通路径；按类型注册表筛选。此过程不需要再调用模型进行分类。
4. **按类型筛选**。Markdown/HTML 必须匹配本轮有效 changed path；Office/PDF/音视频没有这个条件。
   `v4/useAssistantPreviewCardsForRow.ts:80-119` 仅按需要查询本轮变更；
   `lib/assistantPreviewCards.ts:333-357` 和 `packages/shared/src/conversation-preview-artifacts.ts:317-375` 执行门控。
5. **构建与校验卡片**。`assistantPreviewCards.ts:232-264` 从路径末段取 title，从类型表取副标题，
   `:370-379` 按最后出现位置优先排序并去重。最多取 15 个候选，
   `assistantPreviewCardValidation.ts:44-70` 调用工作区 `checkFilesExist` 后最多显示 10 个。
   前端接线见 `AssistantPreviewCards.tsx:101-167`。

```text
文件先已生成
  → 助手正文引用路径 / citation
  → 前端抽取路径与文件类型
  → md/html 关联本轮变更；其他支持类型按各自规则
  → 去重、存在性校验
  → 生成预览卡片
```

一个重要语义边界：`zcodeFileCitation.ts:76-78` 虽然解析 `purpose`，这条卡片链没有用它区分 source/output；
`resolveZCodeFileCitationPreviewKind` 只消费 path/artifactKind。
因此既有 PDF 或 Office 文件即使作为 source 引用，也可能生成预览卡，卡片不证明“本轮新建了此文件”。
反过来，只写了一个文件但正文没有任何可识别引用，也不会仅凭 changed files 自动进入这条预览卡链。
这些边界同时由 `reference/zcode/docs/ui/assistant-preview-cards.md` 说明，不能把“预览卡”误称为严格的“新增交付物登记”。

### deepseek-harness：经 present 登记后生成产物文件卡片

模型可见的 `present` 是单独注册的工具，不是文件写入操作。
其 description 明确要求文件已经存在、已完成，并说明 Host 可以在回合结束后展示。
共用提示词也指导模型用 present 发布便于单独访问的完整交付物，不用它逐个列出修改过的源码。
出处：`packages/deliverables/tool-present/src/index.ts:38-57`；
`packages/deliverables/deliverable-file-references/src/index.ts:12-18`。

实际参数形状如下，description 由模型提供，是可选的：

```json
{"files":[{"path":"output/report.pdf","description":"分析报告"}]}
```

从执行到界面的链路：

1. `tool-present/src/index.ts:78-98` 按 Session 当前 cwd 解析路径，检查文件存在且为普通文件，
   转换成已解析的进程路径；只检查元数据，不读取、生成或复制文件字节。
2. `:101-108` 在成功的最终 `tools/result` 后才追加 `deliverables/presented`，
   数据为 `{turn, callId, files:[{path,description?}]}`。工具被阻止或失败不发布。
   事件形状见 `tool-present/src/types.ts:4-15`。
3. `packages/client/ui-deliverables/src/client/turn-deliverables.ts:175-200` 按 turn 消费该事件，
   保存原事件 seq 和 files 原始 index；`:261-264` 对同一路径取本轮最后一次声明。
4. `client/Deliverables.tsx:45-48,95-120` 读取 presented 并渲染 `PresentedFileCard`，
   不依赖助手最终正文是否再提及它。
5. 系统打开使用 sessionId/seq/index 回查原声明，再检查文件当前存在及 Host 路径映射，
   见 `src/present-open.ts:87-123`。这避免只信任浏览器传来的任意“交付路径”。

```text
write / shell / 文档工具 → 磁盘上已存在最终文件
                                 ↓
模型调用 present(files) → Host 校验 → 成功结果 → deliverables/presented
                                                   ↓
                                      本轮 presented → 回合末正式交付卡
```

交付事件保存的是路径和说明，打开的是当前源文件。文件后来修改，打开内容随之变化；
删除或移动后原声明不能恢复内容。它没有上传一份附件，也没有冻结交付版本。
Session 归属取自工具执行上下文；子代理的声明不会自动成为父代理的交付，父代理需要自行调用 present。

### Harness 的三份集合不要混用

| 集合 | 来源 | 当前消费 |
| --- | --- | --- |
| produced | 成功 write/edit/修改型 str_replace_editor 的调用与结果路径 | 给正文行内文件名提供已知目标词表 |
| presented | 成功 present 追加的 deliverables/presented | 产物文件卡片，以及正文文件词表 |
| changes | workspace/changes 指向的首尾快照净变化 | 改动文件卡与审查 |

`turn-deliverables.ts:60-123,202-223` 先按 callId 配对调用与成功结果，从结果 meta.path 取得实际目标；
旧记录才使用参数路径。`producedForClosing` 在 `:148-159` 去重。
`client/index.ts:106-114` 将 produced 与 presented 合并给行内引用解析器；
但 `Deliverables.tsx:45-48` 挂卡条件只有 changes 或 presented，**produced 不直接生成产物文件卡片**。
所以 shell 生成的文件可以被 Git 记进 changes，但要出现产物文件卡片仍需 present；
文件未在本轮改过，也可以通过 present 将既有文件交给用户。

按以上源码可判定的代表场景（源码分析，不标记为产品真机测试）：

| 场景 | ZCode 的产物文件卡片链 | Harness 的产物文件卡片链 |
| --- | --- | --- |
| 写好 report.md，正文引用，且本轮有效改动包含它 | 可以产生卡片，通过存在性与候选限额后显示 | 仅正文引用不产生卡片；需要 present |
| 文件生成后正文未引用；Harness 另调用 present | 此链没有正文候选便不产生卡片 | 可以产生卡片 |
| 引用既有 report.pdf，没有改动 | 可以产生预览卡片 | 需要 present，且可交付既有文件 |
| shell 生成文件，既不引用也不 present | 此链不产生卡片 | 不产生卡片；变化可能进入 changes |
| 路径不存在 | 候选被存在性校验过滤 | present 失败，不发布交付事件 |

以上是同一种“产物文件卡片”的不同数据获取方式，不另设“普通预览卡”和“正式交付卡”两个产品概念。

### im-2.0：report_outputs 申报，收尾发布产物与其他变更

实读仓库为 `C:/Users/u/Desktop/im-2.0`。产出申报实现位于已有远端跟踪分支
`origin/feat/agent-todo-planning`，核对版本为 `499c0d80e7631349acbd800a05c81a8d89872440`。
当前检出的 master 为旧版 `18bed39fb23aad4d91e7f48945609082a2b28515`；只检查工作树会漏掉该能力。
`agent_page` 已由用户明确标为过时页面，不作为本节对能力有无的证据。
本节通过 git show 读取功能分支，没有切分支、修改仓库或启动应用。

关键文档是该分支的 `docs/native/deliverables.md`（产出文件与变更事件契约）和
`docs/plans/2026-10-23-report-outputs-deliverables-impl-plan.md`（双槽申报与收尾三层数据）。
其核心思想是：模型按任务语义选出成果与过程文件，客户端完成路径归一、路由、去重、求差及收尾发布。

```text
文件工具 / 命令生成文件 → 写工具回执附宿主真实路径
                                     ↓
模型调用 report_outputs(deliverables, byproducts)
  → 工具返回申报回执
  → 工具事件桥照常发 tool_output，并构造 deliverables 结构化事件
  → runtime 捕获申报，流中不上行，多次调用取最后一次完整申报
  → 正常收尾 / ask_user 挂起：发最终 deliverables
  → 时间窗扫描 − deliverables − byproducts：发 workspace_changes
  → 两事件进入实时流及 event_stream 回放记录，前端按事件渲染
```

1. **模型申报两个槽**：`agent/runtime/tools/report-outputs-tool.js:66-132` 实现
   `deliverables:[{path,note?}]`（最终成果，必填非空）和 `byproducts:[{path,note?}]`（过程文件，选填）。
   handler 将斜杠归一、大小写不敏感去重，每槽最多 20 条；两槽相同路径优先保留在 deliverables。
   `.tmp/_work` 路径段自动从成果槽移入过程槽；只剩过程文件而没有成果时返回错误。
   schema 要求宿主绝对路径，但 handler 没有额外执行绝对路径形状校验。
2. **模型为何会调用**：`agent/runtime/prompt/system-prompt.js:727` 要求任务产出文件时在回答结束前申报，
   过程文件进 byproducts、输入文件不申报、主代理汇总子代理产出，后一次整体覆盖前一次。
   `agent/runtime/tools/langchain-tools.mjs:55-67` 注册对应模型工具。
3. **工具输出与独立产物事件的关系**：`deepagents-support/tool-event-bridge.mjs:214-235`
   在工具调用返回后，额外从 report_outputs 的参数构造 deliverables 载荷，同时继续发送普通 tool_output。
   所以卡片消费专门的 deliverables 事件，不需要把任意写工具 stdout 再猜成产物。
   写工具回执追加 `[saved to host path: ...]`，见同文件 `:164-178,224-229`，供模型申报实际宿主路径。
4. **收尾发布**：`agent/runtime/sidecar/runtime.mjs:170-200` 拦截流中 deliverables，
   只保留最后一次完整双槽数据；`:1194-1264` 在正常轮和 ask_user 挂起轮统一发布最终版，
   error/abort 轮不发。事件包含 deliverables/byproducts/inferred；真实申报保留 tool_name/tool_call_id。
5. **其他变化求差**：同文件 `:1267-1290` 扫描 workspace 与 allowedRoots，
   减去两个申报槽后发 workspace_changes。扫描实现为 `deepagents-support/deliverables.mjs:212-286`：
   按本请求开始后的 mtime 收集当前普通文件、包含 `.tmp/_work`、排除 node_modules/.git、最多 200 项。
   这是时间窗变更发现，不是 Git 净 diff：没有增删行数、删除记录或 before/after 版本。
6. **漏申报补偿**：`deepagents-support/deliverables.mjs:89-120` 在模型下一次调用前，
   发现本轮已声称生成文件但没有 report_outputs 调用时注入一次催报；`:127-207` 在收尾仍无申报时，
   从最终回答提取文件名并与本轮 mtime 扫描匹配，合成 inferred=true 的产物事件。
   合成只用于正常收尾，不用于 ask_user 的半程正文；按 basename 匹配不保证唯一归因。
7. **回放记录**：`agent/runtime/conversation/event-stream-recorder.mjs:20-29,97-115`
   将 deliverables/workspace_changes 列为可回放事件，载荷原样保存；普通 tool_output 则有 8 KiB 截断。
   runtime 在两事件发出之后序列化并上传 event_stream，见 `sidecar/runtime.mjs:1302` 起。

前端契约将数据分为：成果主位卡片、过程文件折叠、其他未申报变化折叠；这是产物卡片与下方列表的数据分类，
不是另外发明两类产物卡片。note 来自模型，路径为统一正斜杠形式；打开使用 native.openItem。

**存在性边界与 Harness 不同**：工具会 stat 文件，但只在回执显示 ok/missing；
不存在的申报路径仍保留在 deliverables，事件桥也不做存在性过滤，依靠模型纠错重报。
出处为 `report-outputs-tool.js:104-131` 与 `tool-event-bridge.mjs:97-103`。
因此“已申报”不等于“客户端已确认该成果存在”，正文推断也应保留 inferred 标识。

为不切换用户工作树，已将上述固定版本的相关源码与文档导出至
`tmp/file-feature-research/im2-output-branch/`，来源记录在 source.json。

### 三者如何评价：按产物卡片的行为逐项比较

以下评价只针对上述固定版本的产物文件卡片链，不外推到 ZCode 的 workflow artifact 系统，
也不把改动列表的能力合并成对整款产品的排名。

| 维度 | ZCode | deepseek-harness | im-2.0 功能分支 |
| --- | --- | --- | --- |
| 产物来源 | 助手正文路径、Markdown 链接或 citation | 模型调用 present | 模型调用 report_outputs；未申报时有推断补全 |
| 成果与过程的区分 | 类型和引用规则；purpose 未用于成果分类 | 只显式交付模型选中的文件，其他变更另算 | deliverables/byproducts 双槽，明确表达最终成果与中间文件 |
| 入口校验 | 文件卡显示前过滤不存在候选 | 解析真实目标，存在且为普通文件后成功登记 | 不存在只在回执标 missing，声明仍会发布 |
| 文件类型 | 受前端预览类型表限制 | present 接受任意可访问普通文件 | 工具申报不按扩展名限制；当前 handler 也未拦不存在路径 |
| 多次声明 | 正文引用聚合后去重 | 同一路径取最后声明，不同路径累计 | 每次整体覆盖前一次，收尾发布最后完整清单 |
| 漏报处理 | 正文出现支持类型引用即可；无引用没有候选 | 实读链中未见催报或正文合成 | 下一次模型调用前催报一次；收尾按正文与 mtime 合成 inferred=true |
| 重开对话 | 从保存的正文重建并重新检查源文件 | 保存声明事件，打开当前源文件 | event_stream 保存终态事件，打开当前源文件 |

来源为上面三条完整链。额外比较依据：ZCode 类型表见
`packages/shared/src/conversation-preview-artifacts.ts:50-95`；Harness 的多次声明合并见
`packages/client/ui-deliverables/src/client/turn-deliverables.ts:255-264`，源文件存续边界见
`packages/deliverables/tool-present/README.zh.md:92-94`。

**产品语义判断**：用户要的是“明确交给我的最终文件”，结构化工具申报更直接。
im-2.0 的双槽与收尾事件适合同时整理成果和过程文件；但双槽只提供分类出口，不保证模型分类正确。
Harness 的单个 files 槽已能表示“只交这些文件”，没有 byproducts 不等于无法区分成果与过程。
ZCode 正文提取的好处是无需另一次工具申报、容易与现有消息渲染结合；代价是卡片受回答措辞及类型表影响，
作为 source 引用的既有 PDF 也可能成为卡片。三者都依赖模型表达展示意图，只是表达载体不同。

**可靠性判断**：Harness 的文件解析与成功登记边界更扎实。im-2.0 存在性检查仅反馈 missing，
会保留打不开的申报；其正文/mtime 推断还能同时命中多个同名文件，inferred 必须保留。
催报和推断增加了补偿手段，但没有同任务对照测试，不能宣称漏报率或总体准确率已经优于另两家。

**生命周期取舍**：im-2.0 整体替换有利于去掉旧草稿，但要求后一次提交完整清单，
模型只报新增文件会丢掉前一次成果；Harness 按路径累计较容易分批交付，但也会保留模型未主动撤回的旧文件。
三者此处的卡片链都不自动冻结产物字节；历史卡片与历史文件版本持久化需要分开处理。

**对 Cogent 的建议**：采用结构化产物申报表达成果身份，借用 im-2.0 的收尾定稿和必要的过程分类，
同时使用 Harness 的“路径解析、存在且为普通文件后才发布”标准。正文引用提取可以作为补充入口，
不直接升级为已确认产物。此为调研建议，不是获批实施方案。
改动列表另行选择技术：im-2.0 的 mtime 扫描不能代替 Harness 的快照净 diff、增删行数和逐文件审查。

## 4. 改动清单：先明确比较的两个版本

| 口径 | 比较对象 | 用途 |
| --- | --- | --- |
| 单次工具变更 | 工具执行前 → 执行后 | 过程中的 edit 工具卡 |
| 用户回合净变更 | 本次请求开始时 → 本次请求收尾时 | 回答下方的文件清单与统计 |
| 会话累计净变更 | 会话基线 → 所选结束点 | 会话审查 |
| Git 工作区差异 | HEAD/index → 当前工作树 | 提交前审查、版本控制面板 |

例如同一行 `A → B → C → A`，过程卡确实有三次修改，但该回合最终净变更为零。
所以不能把每次工具的 `+/-` 相加，也不能把所有工具 diff 文本直接拼接当作净 diff。
`git diff HEAD` 会包含用户开始前的修改，普通 `git diff` 还不能完整覆盖未跟踪的新文件。

### 路线一：在实际文件修改边界捕获前后内容

每个回合、每个规范化路径保留首次修改前的内容，以及最后的内容；然后对这两个版本重新算 diff。
新建文件的一侧为不存在，删除文件的另一侧为不存在；移动应保留旧路径和新路径。
追踪点应靠近真正的文件修改操作，不能只记录模型计划调用的参数；工具可能失败，也可能失败前已经部分写入。

优点是归属明确、不需要 Git，也能记录被忽略文件和工作区之外明确获准的目标。
边界是只能看到经过该文件能力的写入；shell、格式化器、脚本、外部进程和某些 MCP 工具的副作用不会自动经过它。
若直到工具完成通知才读取旧内容，旧版本已经不存在，必须提前捕获或由执行器返回已提交变更。

### 路线二：捕获工作区快照，再比较首尾

在请求开始前捕获工作树状态，等待工具和文件操作实际收尾后捕获第二份。
Git 可作为内容寻址存储：私有 index 收集文件，`write-tree` 得到不可变 tree id，
两棵树之间计算路径、增删行数和 hunks。内部快照不是要求用户提交代码。

私有 index 避免改动用户暂存区；私有 object store 或独立快照仓库可进一步隔离对象。
若对象没有可达引用或独立保留策略，GC 会影响长期读取；快照持久化与保留周期必须一起设计。
“使用了 Git”不等于“改变了当前分支”，也不等于“需要向用户展示一个 commit”。

优点是能看到快照范围内由终端、脚本、格式化器造成的结果。
边界是它观测的是时间区间内的工作区变化：用户、另一个会话或后台工具同期修改也会被算进去。
`.gitignore`、未跟踪大文件、嵌套仓库、submodule、LFS/clean filter、非 Git 目录都有各自覆盖和成本问题。
文件系统 watcher 可以提供失效或候选路径信号，但没有旧内容，也不能自行证明写入者身份，不能单独承担可审查和撤销的事实源。

### 路线三：工具捕获与工作区快照结合

deepseek-harness 的 `packages/deliverables/workspace-changes/src/index.ts:145-186` 同时接入顶层回合事件、
工具前置等待和文件 write/edit/delete intent；`recorder.ts:131-164` 保存首份内容与基线。
收尾时 `recorder.ts:300-364` 比较 Git 树，再补充 Git 没覆盖到的文件工具目标。
同一文件以统一路径合并，Git 覆盖到的路径不重复统计；首尾一致不列入。

其 Git 机制见 `git.ts:127-168,231-238`：
`GIT_INDEX_FILE` 隔离 index，`GIT_OBJECT_DIRECTORY` 存自己的对象，
`GIT_ALTERNATE_OBJECT_DIRECTORIES` 只读借用原仓对象，`diff-tree -r -M --numstat` 计算摘要。
该实现的文档也明确指出 split index、git-lfs 等仍可能在原仓产生附带写入，不能把“私有环境变量”直接当作绝对零副作用证明。

这条组合路线较符合 Cogent 的桌面工作流：既有 edit/write，也有 PowerShell/bash 和 MCP。
但建议保留来源与覆盖信息：工具捕获能说明经过了本会话的文件操作，工作区快照只能说明回合期间观察到变化。
两者不一致时不能伪造精确归因。非 Git 目录中的 shell 全覆盖仍需另行做目录快照/影子仓库及排除规则，
不能因为参考实现暂缓，就断言 Cogent 永远不该支持。

## 6. 审查、打开、撤销不能共用“当前文件内容”这一个来源

**打开**通常查看当前磁盘版本；**审查该回合**必须查看该回合冻结的 before/after，
否则后面一轮、用户编辑或格式化器已经改了文件，旧卡片展示的历史就会跟着变。
摘要只需路径、变更类型、行数和版本引用；点“审查”时再按引用加载内容或 hunk，不必把所有全文广播到消息流。
二进制、超大文件、对比超时应保留明确状态，未知行数不能伪装成 `+0 -0`。
纯重命名也需要结构化路径状态，不能要求每个变化都有非空文本 diff。
例如 Codex `turn_diff_tracker_tests.rs:218-231` 明确测试纯重命名没有净文本 diff，不能把这个 tracker 的输出当作完整文件变更目录。

**撤销**则要把当前磁盘与回合 after 比较，再决定能否安全还原 before。
如果后来已被修改，不能直接用旧内容覆盖；可返回冲突供用户处理，或设计真正的三方合并。
ZCode `apps/zcode-cli/packages/core/src/runtime/methods/file-rewind.ts:406-449` 逆序模拟回退，
逐操作检查当前 hash 是否等于预期 after hash，不一致标记 `external_modified`。
回退多轮时必须按依赖顺序计算，不能只找最旧 before 就盲写磁盘。

文件回退与聊天回退也是两个不同动作。Claude Code 和 Cline 提供各自选择；Cursor 文档明确恢复文件不删除聊天。
按钮文案应对应实际能力，不能让一个“撤销”隐含清掉后续对话或其他用户修改。

## 7. Cogent 现状与建议落点

当前实读事实：

- `src/host/runtime/session.ts:394-399,2000-2025` 从工具 result.details 抽出展示 diff，
  在 `:2208-2215` 从历史 toolResult.details 恢复；`components/ui/tool.tsx:53-75,163-175` 显示 edit diff 与计数。
  pi 的 write 没有对应 before/diff，不能把现状写成 edit/write 均具备完整 diff。
- `src/renderer/src/components/ui/markdown.tsx:84-99` 对链接统一 `window.open(href)`；
  `src/electron/main/index.ts:75-80` 的打开守卫处理 HTTP(S)。本地文件解析和专用跳转尚未接入正文。
- `src/electron/main/ipc/workspace.ts:28-34` 已有 `shell.openPath` 能力，可作系统打开入口，
  但不等于有内部文件预览、编辑器行号定位或历史 diff 查看器。
- `src/host/runtime/session.ts:330-359` 明确一个 run 包含多轮模型/工具循环，
  `reference/pi/packages/coding-agent/src/core/extensions/types.ts:1053-1058,1078-1092` 区分 agent_settled 和 turn_end。
  因此回答底部的汇总应跟用户请求/run 对齐，不能在每个 pi turn_end 都当成用户回合结束。

以下是建议，尚未实现：

1. **统一文件引用与打开合同**：路径、来源工作区/Host、可选行列号；Markdown 链接、行内引用、工具路径、交付物卡和改动行都消费它。
2. **Host 拥有变更事实**：首个获准的可能副作用工具前准备基线；实际文件能力补捕获 before/after。
   深入调研后的推荐存储为原始字节内容快照，详见待审计划；不把 Git 作为完整覆盖的前提。
   快照准备必须先于工具执行，不能异步旁路后让写入抢跑。
3. **为请求保持稳定身份**：保存 session、用户消息/run 标识和来源工作区；停止/失败也等待已发生文件操作收尾并结算。
   不能只监听“成功终答”，也不能按当前选中会话归属异步返回的数据。
4. **持久化摘要与可读版本**：摘要进会话侧记录，内容进按内容去重的存储或持久快照；保留策略和索引一起维护。
   不把大量 before/after 文本塞进模型上下文，也不把只有内存缓存的卡片宣传成重启可恢复。
5. **前端两种消费方式**：结束后展示轻量改动清单，逐文件按需加载 diff；正文链接直接引用已有文件目标。
   汇总按首尾重算，行数按 diff hunk 计算，不能把 `+++` / `---` 头也当作正文变动行。
6. **完整交互可以共享底座**：文件类型图标、内部文本/Markdown 预览、打开到编辑器、复制/定位路径、回合 diff 与逐文件/整轮撤销都围绕同一记录服务组织。
   便宜且有用的打开/定位能力没有必要因为参考仓分期就删掉；涉及冲突的回退明确校验当前版本。

```text
owner: Host = 基线/内容/摘要；renderer = 卡片与按需详情；main = 桌面打开
受理用户请求 → 稳定请求身份 → 基线准备完成 → 模型/工具循环
                                           ├─ 文件工具捕获
                                           └─ shell / MCP 执行
正常/停止/失败 → 已发生操作收尾 → 最终快照 + 净差异 → 内容与摘要持久化
                                                    ↓
                             终态事件/查询 → renderer 回合清单
                                           ├─ 打开当前文件 → main/预览
                                           ├─ 审查冻结版本 → Host 按需详情
                                           └─ 撤销 → 校验当前版本 → 还原/冲突
```
