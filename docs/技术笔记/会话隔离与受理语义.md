# 会话隔离与受理语义

> 主题：实例隔离、导航身份与长任务受理。运行生命周期见
> [pi接入与会话托管](pi接入与会话托管.md)，现状见 [会话与对话](../模块/会话与对话.md)。

## 1. 隔离有两半

每会话独立转录只能保证内核隔离，不能保证 UI 发往正确的 sessionId。
“新聊天”若只清画面、提交仍用旧 id，模型收到的就是旧历史；引擎并没有跨会话污染。
复现必须捕获实际外发请求体，区分显示状态、协议路由和 provider 行为，不能仅从回复
话题接近就归因于 provider 串话。

原串话复现中，“新聊天”后的请求含旧设计问答，真正新 id 的请求只有 system 与新问候。
中断的半截问候本已保留在转录，后来重新出现是历史回放，不是模型凭空记住了别的会话。
一次复现脚本又把 user 的 block 数组当字符串匹配，导致截断分支没触发，曾产生错误结论。
探针要先证明它实际走到目标分支；脚本的 FAIL 不能直接当产品的 FAIL。

## 2. pi 的边界与 Host 的受理窗口

pi `Agent` 每实例持独立 messages，prompt 取上下文快照
（原接入核对的 `pi-agent-core/dist/agent.js:30,246,300`）。busy 检查在 async prompt
中报错，表现为 Promise reject；外层同步 try/catch 接不住未 await 的 Promise。

```text
owner: Host SessionManager（会话存在性、busy 与运行预约）
RPC submit → 同步校验 → 建立本次操作 owner → 返回 accepted
                              └─ 异步装配/执行 → 协议进度与权威终态
owner: renderer（当前视图、草稿与请求代次）
```

Host 的 busy 必须覆盖受理到 agent_settled 全程。只检查 pi.isStreaming，会在准备、
内聚恢复或续写间隙放进第二条 prompt。未知会话、无效根、busy 等入口失败返回 RPC 错误；
受理后的执行失败再走 run.failed。丢掉 submit Promise 让异步拒绝逃出 dispatch，可能变成
unhandledRejection 并拖垮整个 Host。

中断文本仍归转录，消息级 aborted/error 继续经过 message_end/turn_end
（`reference/pi/packages/agent/src/agent-loop.ts:250-264`）。Host 终态快照与 renderer
本地占位有明确覆盖关系，不能以“失败就清空”制造 UI 与模型上下文两种历史。

## 3. 新聊天与恢复初始化

导航与首次发送分开拥有身份：

- load 只恢复，不因活跃列表为空就自动造持久化会话。首装与全部归档都允许空列表。
- 所有新聊天入口都回到唯一未发送草稿；从已有聊天进入、重复点击、选择/解绑项目均不建空会话。
  草稿身份独立于当前视图，切 A 再回来仍能找到正文、文件和暂存项目/权限/计划。
- submit 以 new 视图优先并返回实际目标 id；受理后将原草稿交给该聊天，轮换未发送入口身份。
  await 后不能读当前活动 ID 猜归属；创建迟到不抢用户已打开的其他聊天。

恢复未发送入口时，若旧版保存的 ID 已出现在聊天草稿绑定中，只轮换入口 ID，保留原聊天草稿与绑定；
否则新入口与已创建聊天会读写同一份正文/附件。未绑定的旧入口继续复用，不能以升级为由清空。

为何不让 load 造会话：归档最后一条后的空集合是合法终态，不等于待初始化。
StrictMode 双挂载还会把“空则创建”放大为并发双建。启动和导航的幂等性要从持久化
实体数量验证，不能只看画面是否空白。

这层导航去重不属于 pi。pi `SessionManager.newSession` 每次重设 id、条目与索引并
选择文件路径（`reference/pi/packages/coding-agent/src/core/session-manager.ts:1065-1088`），
它不知道桌面主体是否已经处于新聊天。唯一未发送草稿与导航所有权由 Cogent 自己承担。

## 4. 状态为什么按会话分桶

一个 `bySession[sid]` 桶包含该会话消息、运行态、挂起输入与回合结果，删除一键就清完整桶。
多份平行 Map 依靠 helper 枚举删除，漏一个 Map 编译器也不会发现；单桶的类型关系更完整。
未落桶 selector 的数组缺省必须引用稳定常量，不能每次返回新的 `[]`。

侧栏的每个 ChatRow 直接按自身 sessionId 订阅 `runtime.running / compacting` 的布尔值，
用 shadcn Spinner 呈现工作状态，固定行尾定位，动作簇显现时原位隐藏，避免标题内边距
变化带动 spinner。导航选择不拥有运行位，所以后台聊天也能显示；
消息增量虽然更新桶，但工作布尔值不变时不会引发该行重渲染。等待审批标签优先。

zcode 对照：`reference/zcode/packages/ui/src/store/zcodeSessionStoreTypes.ts:237,554,592`
用 workspace 桶、默认工厂与稳定单例缺省；`zcodeSessionStore.ts` 组合 navigation/
workspace/task 切片，types/selectors 分文件。Cogent 借分桶和稳定缺省，动作仍按会话生命周期
内聚拆文件，不为相同模式额外引入切片组合；删除会话真实删桶，不只增加内存诊断。

## 5. 横向对照与落点

LangGraph 的 thread_id + checkpointer 与 sessionId + 持久化有相同责任分工：id 是调用方
提供的关联键，传错就读错历史。作者此前 DeepAgent 把显示消息与转录混在一起，难以分别
验证；Cogent 保留“引擎真源 → 协议投影 → renderer 按会话分账”的可观察边界。
这些是结构对照，不据历史产品观察推断闭源客户端当前实现。

- `src/host/runtime/session.ts`：受理校验、同步预约、事件转译与持久化；
- `src/renderer/src/features/home/HomeSidebar.tsx`：发起入口与未发送草稿复用；
- `src/renderer/src/stores/home.ts`：视图身份；`stores/chat/`：桶与异步请求代次；
- `tests/renderer/features/home/home-sidebar.render.test.tsx`：从真实按钮覆盖重复点击；
- `tests/renderer/stores/chat/` 与 `tests/integration/`：状态及协议层的独立检查。
