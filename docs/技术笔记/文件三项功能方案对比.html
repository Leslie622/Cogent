2.2 A 和 B 的真正差异：怎样保住“原本指向哪里”

比如模型写 [文件](./src/app.ts)，意思是“当前项目里的 src/app.ts”； [文件](/src/app.ts) 则可能指系统绝对路径。两者不能在清洗后混成一个意思。

因此，B 的路径改写可以工作，ZCode 已经为它补了相应规则；但它不是没有额外约定。 ZCode 自己就有“./foo 被改成 /foo，再判断是否应拼回工作区”的分支。 Cogent 新增这一能力时，选择 A 的封装方式更直接：先保留原目标，后面不需要猜前导 / 是怎么来的。

2.3 最终做法与理由

  1. 让模型写标准链接，内部采用 A 的封装。 在安全处理前保存原始本地目标，编码为专用片段；自定义组件解码后交给 Host。 内部编码不写进模型回答或历史转录，不新增模型要学习的 citation 指令；Host 仍核对会话与文件范围，编码本身不授予读盘权限。 拆封装只还原传输内容；文件名中的百分号再按目标语法解码一次，不能把字面 %20 误变成空格。
  2. Windows 恢复借用 ZCode 的方法。 反斜杠可能在 Markdown 解析期已被当作转义吃掉，须按原文位置恢复并校验，不能在点击时猜。 同时保留 Streamdown 默认安全插件；完整链接可在流式中打开，未完成标记不可打开，不逐 token 查询磁盘。
  3. 反引号文件名借用 Harness 的唯一匹配。 词表扩展到本轮真实读过、写过、申报过及记录到变化的文件。 两个根都有 index.ts 时，单写这个名字不自动选一个；完整路径仍可点击。代码围栏、命令和链接内部不再嵌套文件按钮。
  4. 三个入口共用一个打开器。 相对路径绑定消息当时的主根；点击默认右侧只读面板，窄窗用 Dialog；支持行、列、范围、复制、定位、系统打开、另存和已配置编辑器。 旧消息缺少历史根信息时明示按当前根解析，不假装能还原从未保存的来源。

共用预览采用 A 的能力划分：源码只读定位；Markdown 渲染／源码切换；图片缩放；PDF 按页视觉预览； Office 复用现有 worker 做文字、工作表和页序内容预览；音视频使用可解码的原生控件；其他类型仍有文件信息与系统动作。 PDF 与 Office 分开，是因为现有 PDF.js 可以渲染 PDF 页面，Office 的原生排版另需引擎。 这两者都还需要界面接入和资源管理，并非“已有解析器，接一个 fileId 就全部完成”。HTML／脚本默认显示源码。

3. ② 正文下方的产物文件卡片

3.1 四种做法

对象 谁决定“交付哪些文件” 多次申报、历史与故障 优点与代价
ZCode 从本轮助手各段正文提取链接、路径、citation，再按支持类型、是否改动和存在性筛选 最新助手行完成或被打断后可建卡；Markdown/HTML 要匹配本轮有效改动，Office/PDF 等不要求；所查卡片链按源路径打开 不多调用工具，但回答措辞和类型表会影响出卡；引用既有 PDF 作参考也可能出卡；卡片不是严格的交付声明
Harness 模型调用 present({files:[{path,description?}]})，Host 校验存在且为普通文件后记结构化事件 本轮多次调用累积不同路径，同路径取最后说明；不能用空数组清空；声明可回放，但不复制字节，打开的是当前源文件 交付意图清楚、校验扎实、UI 不依赖正文解析；源文件后来删除或改写，原交付内容无法由声明保证

B report_outputs({deliverables})，只有交付文件，其他变化交给列表 替换、清空、校验、副本与 A 接近；取消催报，保留推断补卡 工具更简单，符合当前需求；推断依然可能把普通修改当产物，甚至把显式清空的卡补回来

源码依据： ZCode 提取引用、 类型与改动门槛、 完成或打断条件、 存在性筛选； Harness 校验与事件、 多次申报合并。

两个例子能看清差异：

  • “我参考了这个旧 PDF”：正文链接应可点；是否要出产物卡，应取决于有没有明确交付它。ZCode 的这条候选链不能严格区分。
  • “把这个既有 ZIP 交给我”：它没被本轮修改，也未必能内置预览，但依然应有产物卡。Harness 和 A/B 的申报路线能表达这个意思。

3.2 对 A、B 的取舍

接受 B 的单槽简化。 当前需求只需要模型说清交付哪些文件；全部变化已经有独立列表。 如果还需要“这是过程文件”的说明，将来可以作为元数据增加，不必现在就让模型填写第二组文件。 不过，A 的 byproducts 本来只是列表标签，不等于第二种卡片；B 用“避免第二种卡片”否定它，理由不够准确。

保留 A 的一次条件提醒，撤回 A/B 的自动推断出卡。 已知一个路径真实且唯一，只能证明“它指向谁”，不能证明“它要交付”。 例如改了一个源码文件、最终回答提到它，A/B 的推断就可能把它升成产物；显式清空后再推断还会破坏撤回语义。 这也是 A 的缺口，不能只批评 B。

明确交付应走结构化工具。提醒只搭载已有下一次模型调用，不为收尾再启动一次模型循环； 仍漏报时，正文链接和改动列表照常可用，但不把推测包装成已申报卡片。 代价是少数漏报会少一张卡；需要用实际任务检查申报成功率，不能声称系统提示已保证永不漏报。

3.3 最终做法与理由

  1. 工具只有一组 deliverables。 每项路径和简短说明，允许各类可访问普通文件，包括既有文件、脚本、ZIP 和临时目录内文件。 修改源码默认进入改动列表；用户要求把源码交给他时也能申报。是否能预览，不作为是否能交付的门槛。
  2. 声明有明确状态。 “未申报”和“已申报空清单”不同；每次有效调用完整替换。 有一项不合法就反馈具体原因、不发布这次替换，上一份有效清单继续有效；空数组是成功撤回。
  3. 像 Harness 一样先验证，再确认。 Host 解析实际目标、核对读取范围、存在性和普通文件；符号链接到真实目标后重新检查。 工具回执给模型看，结构化记录给界面用，前端不解析回执里的自然语言。
  4. 像 A/B 一样保留交付版本。 申报时存一个已确认副本，收尾复核最终版；源文件消失则保留最近确认版并说明。 卡片默认预览／另存交付副本，“打开当前原文件”单独选择；超副本预算仍可交付当前源文件，但明确没有历史副本。
  5. 成功、停止、失败都结算已确认结果。 卡片附带所属回合状态，不能因为任务失败就丢掉已完成文件，也不能把半成品说成已完成成果。 ask_user 挂起不等于回合结束；等待期间用正文链接查看，收尾才在固定尾部呈现卡片。
  6. 提示与撤回规则互不冲突。 系统提示要求终答前申报；有文件活动、仍未申报且已有下一次模型调用时，最多提醒一次“如有需要交付的文件，请申报”。 已有有效声明，包括空清单，就不催报、不由正文自动追加。工具失败后的正常模型纠错不算强开的额外循环。

这样卡片的含义很稳定：模型说要交付，Host 已确认可用。正文提到某文件、工具写过某文件，都不会自动替代这两个条件。

4.2 为什么仍选原始字节，而不直接用 Harness 的 Git 快照

Harness 的思路值得采用：先有起点，再允许工具执行；收尾比较终点；工具精确捕获补漏。 它的 Git 快照也没有必要改用户 index、分支或 refs，不能把“用了 Git”说成“会破坏仓库”。

Cogent 选原始字节有三个具体收益：非 Git 文件夹与没有 Git 的机器使用同一套逻辑； 产物副本和改动历史共用内容存储；原始 CRLF、BOM 与二进制不用经过 Git 的文本属性和过滤器。 Git 也能绕过这些转换保留字节，选择原始字节是减少两套语义与配置维护，不是认定 Git 做不到。

代价同样明确：Git 提供的部分扫描、索引和对象管理，现在要自己处理。 这条路线需要实现一套受限的文件版本记录能力，工作量明显超过列表 UI。 A、B 都承担这个成本；没有完整扫描性能结果前，不能把二者判为比 Harness 更快。 若整体性能不达标，应优化扫描／索引或重新评估 Git 加速，不能为了维护既有决定而放弃实测。

4.3 最终捕获与统计做法

  1. 范围先定清楚。 冻结本轮显式绑定的工作区根，重叠根去重；不扫描整个 Home。 排除版本库内部、依赖缓存和 Cogent 自己的存储，不按 .gitignore 全部排除，避免漏掉 tmp/out 中的真实产物。 嵌套仓库登记为边界，需要跟踪其内部时显式绑定；目录符号链接不自动跟随扩大全量扫描。
  2. 首次获准的潜在写盘工具执行前，共同等待基线。 write/edit、shell 和 MCP 执行都覆盖，不猜 shell 命令是否只读。 直接调用与嵌套 ctx.executeTool 走同一个捕获协调器，审批与最终参数确认后再捕获，拒绝不伪造变化。 纯问答不扫描；记录观察窗口的实际起止时间，不假装是整个用户输入时段的原子快照。
  3. 范围快照为主，工具目标捕获补漏。 有全范围基线时不能被后来的工具 before 覆盖，否则会丢掉此前 shell 的修改。 根外或排除区内的明确工具目标单独捕获；失败工具也检查实际 after。 根外文件若先被未知 shell 改过，后来才被文件工具发现，不能声称已知道整轮最初版本，必须注明覆盖起点和缺失。
  4. 保存原始字节，另算展示差异。 内容按 SHA-256 去重，清单保存路径、类型、模式、hash 和内容是否可用。 区分“确认不存在”“存在但未读完”“未遍历到”；不完整扫描不能据此报删除，未知 before 不能直接当作新建。 读前后状态不稳定时重试一次，仍不稳就标未知，不把整个工作区说成瞬时冻结。
  5. 只显示首尾净变化。 文本在 worker 计算 +N -M；二进制、超大、未知编码或超时保留条目并显示“—／未统计”。 编码、换行、模式、链接目标变化即使没有文本增删也要有条目；内容相同且唯一配对的删除／新增可显示为按内容匹配的改名，歧义仍分开。 快照看到的并发修改称“本轮工作区更改”，不宣称一定由 Agent 独占造成。
  6. 成功、失败、停止均收尾。 等正在进行的捕获完成或记录明确失败，再冻结 after、持久化摘要并释放运行状态。 统计可显示“整理中”并按 revision 更新；旧查询不能覆盖新结果。Host 崩溃后只展示已保存版本，不能拿重启时的磁盘冒充当时终点。

实现挂点依据：pi 的 可等待 tool_call／tool_result； Cogent 的直接与嵌套两条审批入口。 pi edit 的展示 diff 可以继续用于工具过程卡，但 write 不提供旧内容，不能把工具展示文本当作完整历史事实源。

4.4 历史、预算和恢复必须一起说清

历史绑定采用 A 的明确规则。 每个真实用户输入一个 turnId；实际 user entry id 与 turnId 持久关联，纯文本也绑定。 自动续写和手动继续仍属于同一用户回合；每次执行有自己的 executionId。 手动继续复用原始基线和最后有效产物声明，发布同一回合的新 revision，不从中间状态重算一轮。 可继续的截断回合保留原始基线，直到完成或下一个真实用户输入；继续前的外部变化单独记录观察区间。 原始消息 DOM key 不改，旧历史没有的 before 不回填假 diff。

真实用户消息 → 实际 entry id ↔ turnId（持久关联）
                                ├─ 第一次执行：原始基线 → 收尾版本 1
                                └─ 手动继续：同一基线 → 收尾版本 2
界面仍是一轮；产物与改动按最新 revision 更新，历史文件两侧由 Host 保存。

现有可复用缝见真实 entry 写入回调。 B 也提到了这个缝，但尚未写出持久映射与继续时的基线继承，不能把增加一个 optional turnId 字段视为全部接通。

存储长期只保留有用版本。 原始对象库同时服务交付副本和历史 diff；正常收尾后释放未变化文件的基线内容租约， 长期保留变化文件两侧、交付版本和必要清单。仍可继续的截断回合暂留原始基线。 否则每轮把整份工作区内容永久引用住，哪怕有去重也会让存储预算过早耗尽。 删除会话才释放其引用；预览、活动扫描、恢复日志持租约；不悄悄删除仍被历史引用的版本。

初始预算沿用 A 的建议值，集中配置：2 路文件 I/O、每根最多 20,000 文件、内容副本 20 MiB／文件、 交付副本 100 MiB／文件、哈希上限 100 MiB／文件、每轮新增对象 256 MiB、全库 2 GiB、首尾扫描各 10 秒。 这些是待实测的护栏，不是性能成绩；超限保留路径和真实覆盖状态，不能变成“没有修改”。 必须验证完整遍历、读取、写副本、哈希、diff 与 UI，而非只跑内存／哈希微基准。

审查与恢复沿用 A/B 的方向，补齐契约。 默认打开冻结 before/after 的只读 diff，可切统一／双栏；当前文件另有打开动作。 单文件／整轮撤销和重做继续纳入，但单独作为需要完整测试的批次，不再称作便宜附赠功能：

  • 撤销校验当前存在性、类型、模式和内容是否符合 after；重做对照 before 及上次恢复结果。后续编辑冲突就拒绝覆盖。
  • 新建的撤销是删除已匹配的 after，删除的撤销是恢复 before；改名核对两端，不得覆盖新路径上后来出现的文件。
  • 符号链接、硬链接或缺少完整副本的项可以审查，但影响范围不清时不可自动恢复。
  • 整轮先预检，执行前复核；逐项持久记录恢复日志。中途失败只对仍符合预期版本的已执行项补偿，不强行覆盖后来变化。
  • Cogent 内部恢复与同路径操作协调；外部进程仍可能并发写入，不承诺跨文件的原子事务，也不把 hash 预检说成绝对消除了竞态。
  • 恢复只改变文件，不回退聊天；磁盘状态与不可完成项必须如实反馈。恢复日志未结清时，重启不能伪装整轮已恢复。

5. 实施约束与待验证项

建议实施顺序仍是：文件身份与存储 → 正文链接与共用预览 → 申报与产物卡 → 快照与净统计 → 列表、审查与恢复 → 完整联动验收。 本轮没有启动实现；本文是新的决策审阅入口，A/B 保留用于对照。用户认可后再把选定内容统一回写实施计划，避免两份计划同时指挥代码。

审阅时重点看四个结果：文件链接打开的是正确目标；卡片确实表达明确交付；列表算的是声明范围内的首尾净变化； 停止、继续、重启、超预算和用户后改时仍保持上述含义。预算数值、申报成功率和恢复可靠性，都要靠后续实现测试证明。
