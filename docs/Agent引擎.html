Agent 引擎手册

Cogent 的 Agent 能力全部住在独立引擎进程 src/agent-service 里，核心是 每会话一个 pi Agent（@earendil-works/pi-agent-core + pi-ai）。 本手册记录它的架构、协议、对话流程与各模块细节 —— 图文一体，随功能演进持续更新。

当前阶段一句话：纯聊天链路已通（选模型 · 配 key · 流式出字 · 中止）， pi 的工具执行 / 审批 / 思考流等差异化能力尚未接线（见第 5 节）。

1架构总览：三个进程，两层边界

UI 不直接碰引擎。Renderer 经 preload IPC 到 Electron main，main 再经 stdio JSON-RPC 驱动引擎进程。 引擎目录（agent-service / protocol）零 Electron import —— 目录即边界， 任何宿主（现在的 Electron main、以后的测试脚本）实现协议即可驱动引擎。

图 1-1 · 三进程架构。绿色区 = 引擎内部（本手册第 4 节逐一展开）。
为什么引擎是独立进程

pi 是 AI 代码助手同源的 Agent 引擎，依赖重、迭代快。隔离在子进程里：崩溃不连坐、Node 版本可控（spawn 前有版本守卫）、协议天然可测试。

main 是壳不是业务

main 只做三件事：方法白名单代理、事件转发、持有持久化存储（凭据/自定义 provider 定义）。业务判断全部下沉引擎。

key 的安全边界

明文只存在两处：main 的 safeStorage 解密结果（不落明文盘）、引擎进程内存 Map。Renderer 只见「已配置/未配置」布尔位。

2通信协议：newline JSON-RPC

传输层是 stdio 上的一行一帧 JSON（newline-delimited），JSON-RPC 2.0 极简子集。 三种帧：请求（带 id，宿主→引擎）、响应（带 id，引擎→宿主）、事件（无 id，引擎→宿主单向推送）。 协议定义在 src/protocol/types.ts，有兼容性纪律：

  • 只增不破：method / event 名一经发布不可改名、不可删；字段只增 optional；
  • 破坏性变更必须递增 PROTOCOL_VERSION（当前 1），引擎在 initialize 响应里上报；
  • protocol 目录零运行时依赖（纯类型 + 纯函数），任何 Node 版本可加载；
  • 错误码不自造，用 JSON-RPC 标准码（ParseError / InvalidParams / MethodNotFound / InternalError）。
为什么长任务是事件驱动

LLM 循环以分钟计，请求-响应式会让宿主挂死在管道上。所以 agent.submit 受理即返回 { accepted: true }，执行进度全部经事件流（run.* / message.* / 将来的 tool.*）推送 —— 受理与执行分离是整份协议最重要的设计决定。

受理 ≠ 收下就完（2026-11-09 修复）：受理含同步校验（会话存在、会话空闲、模型已知）， 校验失败同步 throw → dispatch 转错误响应帧（忙 = InvalidRequest，不存在 = InternalError）。 校验绝不能放进异步段 —— dispatch 的 try/catch 只包住 handler 同步步，异步拒绝会变成 unhandledRejection 直接崩掉引擎进程（全部会话随之丢失）。

3一次对话的完整时序

从用户按下发送，到气泡落定，一条消息要走完 受理 → 启动 → 流式 → 收尾 四个阶段。 背景色带即阶段分界；箭头颜色区分同步调用（深灰实线）与事件推送（绿虚线）。

图 3-1 · 对话时序泳道图。四条泳道即四个代码位置：stores/chat → ipc/engine → SessionManager → pi。
同步调用 / 请求 事件推送（引擎 → UI，非阻塞） 失败 / 中止路径 受理回执（请求-响应）

一条消息在引擎内的生命周期

⑧⑨⑩ 之间引擎里其实有个不显眼的流式累积缓冲（StreamingState）： messageId 在 submit 时就预生成（UUID），此后每个 text_delta 都往同一个缓冲追加文本并推 delta 事件； turn_end 到达时顺手记下 pi 的 stopReason；agent_end 时缓冲一次性转成完整 ChatMessage 挂在 run.completed 上 —— 所以 UI 流式渲染的是「半成品」， 最终以 completed 的完整消息为准替换，不怕 delta 乱序或丢失。

pi 事件转译处置
message_update只转译 text_delta 增量 → message.delta；thinking / toolcall 增量直接丢弃（呈现属空位 4）
turn_endassistant 消息时记 stopReason 到缓冲（agent_end 事件本身不带此信息）
agent_end定案：有 errorMessage → run.failed；否则缓冲文本 → run.completed
agent_start / message_start / message_end协议暂无对应事件，静默丢弃

4模块详解

4.1 SessionManager（runtime/session.ts）

引擎的业务中枢。持有 Map<sessionId, { summary, agent }>，每个会话一个独立 pi Agent 实例， transcript（对话历史）天然隔离在 agent.state.messages 里 —— 引擎自己不维护消息数组，pi 即存储。

  • 建 Agent：默认模型 anthropic/claude-sonnet-4-5、systemPrompt「You are Cogent, a helpful desktop agent.」、 thinkingLevel off；streamFn 绑 models.streamSimple（auth 解析、provider 分发、重试全部 pi-ai 承担）； getApiKey 回调查凭据表（每轮请求前解析，支持运行中换 key）。
  • submit：可选换模型（先按 provider/model 精确找，再退化为全目录按 id 找）与思考档（六档）； 首条消息自动截 24 字作会话标题（命中后不再覆盖）；发 run.started、开流式缓冲、agent.prompt(text)。
  • session.messages：pi Message[] → ChatMessage[]。只取 user/assistant 的纯文本； system 消息是 prompt 载体不对 UI 暴露；content blocks 也压平成文本（结构化是空位 1）。
  • 会话 id：s-<自增>，引擎重启从 1 重来（持久化是空位 3）。

key 从用户输入到 LLM 请求头，全程不落明文盘、不出 main 进程：

图 4-1 · key 旅程。引擎侧 CredentialRegistry 是 key 的唯一运行时存放点，引擎零磁盘持久化。

4.3 CustomProviderRegistry（runtime/custom-providers.ts）

用户自建的 OpenAI-compatible 端点（中转站 / 网关 / Ollama）。把 pi coding-agent 的 models.json 胶水 换成了「设置页表单 → 协议全量同步」：引擎只收定义、不持久化（宿主落盘，握手 / sync 注入）。

  • 全量替换语义：每次 sync 以传入列表为准 —— 本轮没出现的 custom id 被 deleteProvider 移除；撤掉某条调整（override 清空）= 重新 setProvider 原实例还原。
  • id 空间隔离：自定义 provider 一律 custom/<slug> 前缀，与内置 provider 不冲突。
  • 覆盖 = 委托 + 模型合并：内置 provider 的本地调整版（ProviderOverrideDef：baseUrl 覆盖 + models 用户新增 + disabledModels 目录禁用，2026-11-08 扩展）是同 id 新实例，但 stream / streamSimple 委托原实例闭包 —— 保持 pi 内部的懒加载与重试行为（所以不能用对象浅拷贝，方法绑定原实例状态）； 模型清单 = 目录（滤 disabledModels）∪ 用户新增（ModelDef 构建补默认值），目录快照滞后 / 缺模型由用户补齐。 用户新增模型的 api 取目录首个模型（绝大多数厂商单方言）。
  • 兜底参数：自定义模型（ModelDef 未填的字段）统一 128k 上下文 / 32k 输出、 reasoning: false、input: ['text']（pi 输入模态只有 text | image）、 cost 全 0（计费不可知，UI 不显示价格）。
  • auth 契约：pi 的 ApiKeyAuth.resolve 要求返回 Promise，自定义 provider 的 resolve 以 async 形式满足；未配 key 返回 undefined = provider 未配置。
