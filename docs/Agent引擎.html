Agent 引擎手册

Cogent 的 Agent 能力全部住在独立引擎进程 src/agent-service 里，核心是 每会话一个 pi Agent（@earendil-works/pi-agent-core + pi-ai）。 本手册记录它的架构、协议、对话流程与各模块细节 —— 图文一体，随功能演进持续更新。

当前阶段一句话：工具循环已通 + 上下文压缩完备（批次 1+2 工具/审批 2026-11-10/11；批次 4 压缩 2026-11-12 落地并同日完备化 S1–S8：dsh 同构触发 公式 + 轮间检查点 + L1 prune + 摘要真前缀 + 溢出恢复 + auto-continue + 思考预算通道 + UI 四件），子代理 / MCP 尚未接线（见第 5 节）。

1架构总览：三个进程，两层边界

UI 不直接碰引擎。Renderer 经 preload IPC 到 Electron main，main 再经 stdio JSON-RPC 驱动引擎进程。 引擎目录（agent-service / protocol）零 Electron import —— 目录即边界， 任何宿主（现在的 Electron main、以后的测试脚本）实现协议即可驱动引擎。

图 1-1 · 三进程架构。绿色区 = 引擎内部（本手册第 4 节逐一展开）。
为什么引擎是独立进程

pi 是 AI 代码助手同源的 Agent 引擎，依赖重、迭代快。隔离在子进程里：崩溃不连坐、Node 版本可控（spawn 前有版本守卫）、协议天然可测试。

main 是壳不是业务

main 只做三件事：方法白名单代理、事件转发、持有持久化存储（凭据/自定义 provider 定义）。业务判断全部下沉引擎。

key 的安全边界

明文只存在两处：main 的 safeStorage 解密结果（不落明文盘）、引擎进程内存 Map。Renderer 只见「已配置/未配置」布尔位。

2通信协议：newline JSON-RPC

传输层是 stdio 上的一行一帧 JSON（newline-delimited），JSON-RPC 2.0 极简子集。 三种帧：请求（带 id，宿主→引擎）、响应（带 id，引擎→宿主）、事件（无 id，引擎→宿主单向推送）。 协议定义在 src/protocol/types.ts，有兼容性纪律：

  • 只增不破：method / event 名一经发布不可改名、不可删；字段只增 optional；
  • 破坏性变更必须递增 PROTOCOL_VERSION（当前 1），引擎在 initialize 响应里上报；
  • protocol 目录零运行时依赖（纯类型 + 纯函数），任何 Node 版本可加载；
  • 错误码不自造，用 JSON-RPC 标准码（ParseError / InvalidParams / MethodNotFound / InternalError）。
为什么长任务是事件驱动

LLM 循环以分钟计，请求-响应式会让宿主挂死在管道上。所以 agent.submit 受理即返回 { accepted: true }，执行进度全部经事件流（run.* / message.* / 将来的 tool.*）推送 —— 受理与执行分离是整份协议最重要的设计决定。

受理 ≠ 收下就完（2026-11-09 修复）：受理含同步校验（会话存在、会话空闲、模型已知）， 校验失败同步 throw → dispatch 转错误响应帧（忙 = InvalidRequest，不存在 = InternalError）。 校验绝不能放进异步段 —— dispatch 的 try/catch 只包住 handler 同步步，异步拒绝会变成 unhandledRejection 直接崩掉引擎进程（全部会话随之丢失）。

3一次对话的完整时序

从用户按下发送，到气泡落定，一条消息要走完 受理 → 启动 → 流式 → 收尾 四个阶段。 背景色带即阶段分界；箭头颜色区分同步调用（深灰实线）与事件推送（绿虚线）。

图 3-1 · 对话时序泳道图。四条泳道即四个代码位置：stores/chat → ipc/engine → SessionManager → pi。
同步调用 / 请求 事件推送（引擎 → UI，非阻塞） 失败 / 中止路径 受理回执（请求-响应）

一条消息在引擎内的生命周期

⑧⑨⑩ 之间引擎里其实有个不显眼的流式累积缓冲（StreamingState）： messageId 在 submit 时就预生成（UUID），此后每个 text_delta / thinking_delta 都往同一个缓冲追加文本并推 delta 事件； turn_end 到达时顺手记下 pi 的 stopReason 与用量三件套（usage / durationMs / model，多轮累加）； agent_end 时缓冲一次性转成完整 ChatMessage 挂在 run.completed 上 —— 所以 UI 流式渲染的是「半成品」， 最终以 completed 的完整消息为准替换，不怕 delta 乱序或丢失。

pi 事件转译处置
message_update转译 text_delta / thinking_delta 增量 → message.delta（kind 区分）；toolcall 无增量事件
tool_execution_start / end转译 tool.started（kind/摘要取 tools/ 静态元数据表）/ tool.completed（resultSummary 截 200 字符 + 起止打点）；段化终态（run.completed.messages）按轮封存工具卡，交错保真
turn_endassistant 消息时记 stopReason + 用量三件套到缓冲（agent_end 事件本身不带此信息，此处不摘即永久丢失；usage 多轮累加 = 计费口径）；同时把本轮 text/thinking/工具记录封存成一段 ChatMessage（工具循环段化，D6）
agent_end定案：有 errorMessage → run.failed；否则缓冲文本 → run.completed
agent_start / message_start / message_end协议暂无对应事件，静默丢弃

4模块详解

4.1 SessionManager（runtime/session.ts）

引擎的业务中枢。持有 Map<sessionId, { summary, agent }>，每个会话一个独立 pi Agent 实例， transcript（对话历史）天然隔离在 agent.state.messages 里 —— 引擎自己不维护消息数组，pi 即存储。

  • 建 Agent：默认模型 anthropic/claude-sonnet-4-5、systemPrompt「You are Cogent, a helpful desktop agent.」、 thinkingLevel off；streamFn 绑 models.streamSimple（auth 解析、provider 分发、重试全部 pi-ai 承担）； getApiKey 回调查凭据表（每轮请求前解析，支持运行中换 key）。
  • submit：可选换模型（先按 provider/model 精确找，再退化为全目录按 id 找）与思考档（off + 六档，off 为关闭）； 首条消息自动截 24 字作会话标题（命中后不再覆盖）；发 run.started、开流式缓冲、agent.prompt(text)。
  • session.messages：pi Message[] → ChatMessage[]。只取 user/assistant 的纯文本； system 消息是 prompt 载体不对 UI 暴露；content blocks 压平成文本 + toolCalls 段化投影（2026-11-10；块结构化仍是空位 1）。
  • 会话 id：UUID（持久化后重启不撞号，2026-11-09 起随空位 3 落地）。

key 从用户输入到 LLM 请求头，全程不落明文盘、不出 main 进程：

图 4-1 · key 旅程。引擎侧 CredentialRegistry 是 key 的唯一运行时存放点，引擎零磁盘持久化。

4.3 CustomProviderRegistry（runtime/custom-providers.ts）

用户自建的 OpenAI-compatible 端点（中转站 / 网关 / Ollama）。把 pi coding-agent 的 models.json 胶水 换成了「设置页表单 → 协议全量同步」：引擎只收定义、不持久化（宿主落盘，握手 / sync 注入）。

  • 全量替换语义：每次 sync 以传入列表为准 —— 本轮没出现的 custom id 被 deleteProvider 移除；撤掉某条调整（override 清空）= 重新 setProvider 原实例还原。
  • id 空间隔离：自定义 provider 一律 custom/<slug> 前缀，与内置 provider 不冲突。
  • 覆盖 = 委托 + 模型合并：内置 provider 的本地调整版（ProviderOverrideDef：baseUrl 覆盖 + models 用户新增 + disabledModels 目录禁用，2026-11-08 扩展）是同 id 新实例，但 stream / streamSimple 委托原实例闭包 —— 保持 pi 内部的懒加载与重试行为（所以不能用对象浅拷贝，方法绑定原实例状态）； 模型清单 = 目录（滤 disabledModels）∪ 用户新增（ModelDef 构建补默认值），目录快照滞后 / 缺模型由用户补齐。 用户新增模型的 api 取目录首个模型（绝大多数厂商单方言）。
  • 兜底参数：自定义模型（ModelDef 未填的字段）统一 128k 上下文 / 32k 输出、 reasoning: false、input: ['text']（pi 输入模态只有 text | image）、 cost 全 0（计费不可知，UI 不显示价格）。
  • auth 契约：pi 的 ApiKeyAuth.resolve 要求返回 Promise，自定义 provider 的 resolve 以 async 形式满足；未配 key 返回 undefined = provider 未配置。

4.4 工具系统与审批（tools/ + session.ts 审批矩阵，2026-11-10/11）

引擎的工具能力分两层：工具本体（tools/ 目录，pi 的 AgentTool 声明 + Cogent 的 { tool, kind, summarize } 包装 —— pi 没有"风险类别"概念，ToolKind 是产品语义）与 审批矩阵（session.ts 的 beforeToolCall 钩子，判定逻辑全引擎一处）。 七件工具（批次 3 后）：read / glob / grep / ls（只读不限界，D2 修订：相对路径以基根解析、 绝对任意；walk 尊重 .gitignore/.ignore + 嵌套仓边界）+ write（软限界 resolveWithinRoots， 越界 error 结果带可写根提示）+ edit（精确替换，同 write 边界；diff 进协议 D4）+ bash（D2 单工具平台路由：Windows=PowerShell / unix=bash；killProcessTree + 超时 + tool.progress 流式）。写类（write/edit）与 bash 落盘/执行段走 file-mutation-queue （同文件串行，防并行工具竞态）；输出统一走 truncate 三件套（双上限 + 流式累积器 + 超限临时文件）。

  • 判定矩阵（ToolKind × permissionMode）：read 恒放行；write/edit/bash 按 mode —— auto（完全访问）放行 / plan 直接 block / ask（缺省）先查「始终允许」规则表再发 approval.request 挂起 / autonomous（自主模式，批次 3 D6）write·edit 信任放行、exec 类（bash）照旧询问。规则表（批次 2.5，runtime/approvals.ts）= ~/.cogent/approvals.json 单文件，条目为 roots×kind 快照（只存位置不存 内容），判定 = 会话工作区根与条目任一根交集；优先序 = 软边界（工具执行层越界恒拒） > 规则表放行 > mode 矩阵。mode 读会话 summary 活引用，运行中切换即生效； 矩阵判定在引擎协议层 —— 换壳不改安全语义，UI 只是裁决面板；
  • 权限通告（批次 2.5 D6）：plan/auto 语义以 transcript 内单条 [cogent:permission] system 通告呈现（替换式更新 —— pi 的 systemPrompt 是全部 system 消息重放拼接，纯追加会堆积；ask = 移除）；setPermission 与 ensureAgent 两处驱动，切回 ask 零残留 —— 不进 buildSystemPrompt（leading 固化后运行中切不动）；
  • 挂起手法：beforeToolCall 返回 pending Promise（pi 约定 undefined=放行、 block=拒绝），pendingApprovals 表登记 resolver；三路收尾兜底 —— signal abort listener（挂起必须监听，否则中止后永悬）、会话删除 settleApprovals、disposeAll； 无超时（D5：用户不点就一直等，Claude Code 同款）；
  • pi 时序要点：tool_execution_start 先于 beforeToolCall 发出 （拒绝后 pi 补 end(isError)）—— 挂起期宿主先见 running 卡再见审批卡，三条投影路径 （事件流 / 段化终态 / 历史回查）零特判；
  • 壳侧裁决通道（D3）：main 的 approval:respond 专属 IPC 直抵引擎 approval.respond，不经 renderer 通用代理 —— 审批是安全边界，通道独立 （同「工具结果不经 renderer 转发」同理）；重复裁决 → InvalidParams（双击/竞态显式报错）；
  • 原理与主流对比（Claude Code 规则表 / Codex 沙箱×审批两维 / DeepAgent interrupt）：见 技术笔记 · 工具系统与审批。
