Agent 引擎手册

Cogent 的 Agent 能力全部住在独立引擎进程 src/host 里，内核是 每会话一个 pi AgentSession（@earendil-works/pi-coding-agent 全托管： 工具执行、上下文压缩、JSONL 会话树、provider 路由全用 pi 内置，Cogent 只做会话域服务与协议投影）。 本手册记录它的架构、协议、对话流程与各模块细节 —— 图文一体，随功能演进持续更新。

当前能力一句话：工具循环 + 审批四档 + 上下文压缩 + 用量统计 + 项目域 + 运行时控制台 全部在线；subagent / MCP / HostApi HTTP/WS 通道尚未接线（见第 5 节）。

1架构总览：三个进程，两层边界

UI 不直接碰引擎。Renderer 经 preload IPC 到 Electron main，main 再经 stdio JSON-RPC 驱动引擎进程。 引擎目录（host / protocol）零 Electron import —— 目录即边界， 任何宿主（现在的 Electron main、以后的测试脚本 / 远程 UI）实现协议即可驱动引擎。

图 1-1 · 三进程架构。绿色区 = 引擎内部（本手册第 4 节逐一展开）。
为什么引擎是独立进程

pi 要求 Node ≥22.19，Electron 31 内置 Node 20.15 不满足 —— 进程内集成物理不可行。独立进程另白送崩溃隔离与 headless 模式；Host 跑在自带 node22 上（resources/runtime，spawn 前版本守卫）。

main 是壳不是业务

main 只做三件事：方法白名单代理、事件转发、持有持久化存储（凭据/自定义 provider 定义）。业务判断全部下沉引擎。

key 的安全边界

明文只存在两处：main 的 safeStorage 解密结果（不落明文盘）、引擎进程内存 Map。Renderer 只见「已配置/未配置」布尔位。

2通信协议：newline JSON-RPC

传输层是 stdio 上的一行一帧 JSON（newline-delimited），JSON-RPC 2.0 极简子集。 三种帧：请求（带 id，宿主→引擎）、响应（带 id，引擎→宿主）、事件（无 id，引擎→宿主单向推送）。 协议定义在 src/protocol/types.ts，有兼容性纪律：

  • 只增不破：method / event 名一经发布不可改名、不可删；字段只增 optional；
  • 破坏性变更必须递增 PROTOCOL_VERSION（当前 1），引擎在 initialize 响应里上报；
  • protocol 目录零运行时依赖（纯类型 + 纯函数），任何 Node 版本可加载；
  • 错误码不自造，用 JSON-RPC 标准码（ParseError / InvalidParams / MethodNotFound / InternalError）。
为什么长任务是事件驱动

LLM 循环以分钟计，请求-响应式会让宿主挂死在管道上。所以 agent.submit 受理即返回 { accepted: true }，执行进度全部经事件流（run.* / message.* / 将来的 tool.*）推送 —— 受理与执行分离是整份协议最重要的设计决定。

受理 ≠ 收下就完：agent.submit 在受理前同步校验会话、忙状态与模型， 失败转错误响应帧；受理后先预约运行，再异步装配，失败必须落唯一事件终态。 session.continue 则保留长 RPC：首 await 前预约并发 started，后续校验失败既发 failed 也返回 RPC 错误；取消正常返回，旧回包不能覆盖已到终态。

3一次对话的完整时序

从用户按下发送，到气泡落定，一条消息要走完 受理 → 启动 → 流式 → 收尾 四个阶段。 背景色带即阶段分界；箭头颜色区分同步调用（深灰实线）与事件推送（绿虚线）。

图 3-1 · 对话时序泳道图。四条泳道即四个代码位置：stores/chat → ipc/engine → SessionManager → pi。
同步调用 / 请求 事件推送（引擎 → UI，非阻塞） 失败 / 中止路径 受理回执（请求-响应）

一条消息在引擎内的生命周期

⑧⑨⑩ 之间引擎里有个不显眼的流式累积缓冲（StreamingState）： messageId 在 submit 时就预生成（UUID），此后每个 text_delta / thinking_delta 都往同一个缓冲追加文本并推 delta 事件； turn_end 到达时把本轮 text/thinking/工具记录封存成一段 ChatMessage（工具循环段化），顺手记下 stopReason 与用量三件套（usage / durationMs / model，多轮累加）； agent_settled（pi 在 prompt 生命周期 finally 里每轮恰发一次，晚于全部内聚恢复 —— 单一权威终态）时整段数组 挂在 run.completed.messages 或 run.failed.messages 上。 先读 settled.aborted 判中止，再读 errorMessage 判失败；模型回答成功后在收口钩子中停止也属于中止。 UI 最终直接采用完整分段（含中止尾段，空数组也有效），不再重复追加本地流式占位； stopping 只表示停止请求在途，用户回合头读取按 user.id 保存的 turnOutcomes；新提交不会改掉旧停止/失败头条。 准备期停止先记在 Host 操作对象，不能中断的 await 返回前仍保留预约；尚未交付 pi 的 原始 user 经公开 appendMessage + refreshContext 保存，不因零模型请求丢输入。 continue 的显示快照合并旧前缀与新增段，Inspector 只算本次新增工作。

pi 事件转译处置
message_update转译 text_delta / thinking_delta 增量 → message.delta（kind 区分）；toolcall 无增量事件
tool_execution_start / end转译 tool.started（kind/摘要取静态元数据表）/ tool.completed（resultSummary 截 200 字符 + 起止打点）；段化终态（run.completed.messages）按轮封存工具卡，交错保真
turn_end封存本轮一段 ChatMessage + 记 stopReason 与用量三件套（事件本身不带此信息，此处不摘即永久丢失；usage 多轮累加 = 计费口径）+ 发 context.updated 轮终实报（指示器 run 内实时跟随）
agent_settled定案：aborted 优先 → run.failed(reason:aborted)；其余有 errorMessage → run.failed(reason:error)；否则正常完成或进入 length 自动续写。失败/中止携带完整 messages（含尾段与 usage，允许 []）。恢复先于定案；已释放的 run 不再自动续写
compaction_start / end转译 compaction.started / completed（reason 含 overflow）；阈值压缩发生在触发回合 run 落定后的轮间检查点
其余（agent_start / message_start / message_end / session_info_changed 等）协议暂无对应事件，转译为空（需要时再扩展协议）

4模块详解

4.1 SessionManager（runtime/session.ts）

引擎的会话域服务中枢，经南缝合同（kernel/contract.ts）驱动内核。持有 Map<sessionId, { summary, … }>，每会话一个 pi AgentSession （kernel/pi-session-factory.ts 装配，惰性）。转录真源 = pi 会话树 JSONL （~/.cogent/pi/sessions/，pi 逐条追加落盘）—— 引擎自己不维护消息数组； Cogent 侧只存会话域 summary（v2：~/.cogent/sessions/<id>.json，置顶/归档/权限模式等私域字段）。

  • 惰性装配：启动/恢复只读 summary；首次 submit/compact 才装配 AgentSession（in-flight 去重）； messages() 只读路径永不装配（readPiTranscript 全量回查 JSONL —— 保留式呈现口径， 与上下文口径（pi 投影已裁影子区）分离）。
  • submit：可选换模型（先按 provider/model 精确找，再退化为全目录按 id 找；setModel/setThinkingLevel 判等再调 —— pi 树对"每次调用落一条"的 API 要按需调用，空条目会干扰压缩切点）； 首条消息自动截 24 字作会话标题；streaming 与手动压缩操作 map 覆盖准备、恢复、续写全程。
  • 准备期取消：本次 owner 记录 stopRequested，await 后核对归属；prompt 的 started 回调补取消， 链式 prepareRequest 在原 hook 前后检查 signal。manual compaction_start 补压缩取消；删除后的迟到实例 dispose，已进入 pi 准备的调用另由一次性 core 启动监听补取消。
  • 终态纪律：已进入 pi 的 run 在 agent_settled 定案；未进入 run 的早停与 handled 由 Host 收口。装配失败仍报真实错误；没有 signal 的扩展 await 不能强制终止，需保留预约等待。
  • AUTO_CONTINUE：贴线 maxTokens 截断（pi 不恢复的场景）注入显式 user 续写指令，上限 3 次 —— Cogent 侧保留的唯一运行期干预。
  • v1 旧会话：架构重构前的盘上转录在首次装配时一次性导入 pi 树（kernel/legacy-import.ts），随后重写 v2。

4.3 CustomProviderRegistry（runtime/custom-providers.ts）

用户自建的 OpenAI-compatible 端点（中转站 / 网关 / Ollama）。把 pi coding-agent 的 models.json 胶水 换成了「设置页表单 → 协议全量同步」：引擎只收定义、不持久化（宿主落盘，握手 / sync 注入）。 双注册：同一 createProvider 实例既进 UI 目录（MutableModels）也进 pi 请求路由 （ModelRuntime.registerNativeProvider）—— 单一构造源，两套目录永不分叉。

  • 全量替换语义：每次 sync 以传入列表为准 —— 本轮没出现的 custom id 被 deleteProvider 移除；撤掉某条调整（override 清空）= 重新 setProvider 原实例还原。
  • id 空间隔离：自定义 provider 一律 custom/<slug> 前缀，与内置 provider 不冲突。
  • 覆盖 = 委托 + 模型合并：内置 provider 的本地调整版（ProviderOverrideDef：baseUrl 覆盖 + models 用户新增 + disabledModels 目录禁用）是同 id 新实例，但 stream / streamSimple 委托原实例闭包 —— 保持 pi 内部的懒加载与重试行为（所以不能用对象浅拷贝，方法绑定原实例状态）； 模型清单 = 目录（滤 disabledModels）∪ 用户新增（ModelDef 构建补默认值），目录快照滞后 / 缺模型由用户补齐。 用户新增模型的 api 取目录首个模型（绝大多数厂商单方言）。
  • 兜底参数：自定义模型（ModelDef 未填的字段）统一 128k 上下文 / 32k 输出、 reasoning: false、input: ['text']（pi 输入模态只有 text | image）、 cost 全 0（计费不可知，UI 不显示价格）。
  • auth 契约：pi 的 ApiKeyAuth.resolve 要求返回 Promise，自定义 provider 的 resolve 以 async 形式满足；未配 key 返回 undefined = provider 未配置。

4.4 工具系统与审批（pi 内置工具 + session.ts 审批矩阵）

工具本体 = pi coding-agent 内置 8 工具选 7（read / edit / write / grep / find / ls + shell 位 win=powershell 其他=bash），经 createAgentSession 的 tools allowlist 显式指定。执行、截断护栏、并发写队列（withFileMutationQueue）、 进程树管理全在 pi；Cogent 侧只剩策略投影：工具名与 ToolKind 静态元数据表 （runtime/tool-meta.ts —— pi 内置工具不带 annotations，风险类别是 Cogent 的产品语义）、 写类根内判定（runtime/write-boundary.ts）与 审批矩阵（session.ts decideApproval，factory 链式包裹 agent.beforeToolCall —— 拿回 abort signal， 挂起审批在中止时不永悬）。find/grep 分别 spawn fd/rg（PATH → 自动下载 → error 降级不崩引擎）。

  • 判定矩阵（ToolKind × permissionMode，zcode 对齐）：read 恒放行； auto / autonomous 完全放行（含工作区外写 —— 主流 bypassPermissions / danger-full-access 同款）； plan 拦写/exec；ask（缺省）的 exec 与根内写先查「始终允许」规则表，未命中与越界写都弹 approval.request 挂起（人是最终裁决者，越界请求带 outsideRoots 标记）。 规则表（runtime/approvals.ts）= ~/.cogent/approvals.json 单文件， 条目为 roots×kind 快照（只存位置不存内容，无泄漏面），判定 = 会话工作区根与条目任一根交集； 规则 = 根内信任记忆，永不放行越界写。mode 读会话 summary 活引用，运行中切换即生效； 矩阵判定在引擎协议层 —— 换壳不改安全语义，UI 只是裁决面板；
  • 权限通告（before_agent_start sections）：每轮按活 mode 设系统提示词的 cogent_permission 节（pi 对 sections「变更才追加 patch、回放按名替换」—— 切换下一轮生效、不堆积）；四档全设正向文案（ask 只移除段的话，历史里 plan 拦截的工具 error 会让模型推断"仍只读"连试都不试）；「允许，并切换为 ▾」= 允许本次 + 切会话模式 + 记项目默认（同项目新会话沿用；解析链：显式 > 暂存 > 项目默认 > 全局）；
  • 挂起手法：beforeToolCall 返回 pending Promise（pi 约定 undefined=放行、 block=拒绝），pendingApprovals 表登记 resolver；三路收尾兜底 —— signal abort listener（挂起必须监听，否则中止后永悬）、会话删除 settleApprovals、disposeAll； 无超时（用户不点就一直等，Claude Code 同款）；
  • pi 时序要点：tool_execution_start 先于 beforeToolCall 发出 （拒绝后 pi 补 end(isError)）—— 挂起期宿主先见 running 卡再见审批卡，三条投影路径 （事件流 / 段化终态 / 历史回查）零特判；
  • 壳侧裁决通道：main 的 approval:respond 专属 IPC 直抵引擎 approval.respond，不经 renderer 通用代理 —— 审批是安全边界，通道独立； 重复裁决 → InvalidParams（双击/竞态显式报错）；
  • 原理与主流对比（Claude Code 规则表 / Codex 沙箱×审批两维 / DeepAgent interrupt）：见 技术笔记 · 工具系统与审批。

4.5 上下文压缩（pi 内核 + Cogent 承接面）

压缩内核 = pi AgentSession 内置：触发线 占用 > ctx − reserve(16384)（阈值路） + 溢出路（context overflow：删失败轮 + 压缩 + continue 重试，单次闸），全部发生在 prompt() 生命周期内；摘要请求把被摘要消息文本化序列化进 <conversation> 标签（防续写）； 手动 = session.compact → pi compact。Cogent 侧只做四件承接：

  • 事件转译：compaction_start/end → 协议事件（reason 含 overflow）； summarizedUntil = 保留区首条时间戳；summaryUsage = 摘要调用自身的账；
  • 小窗自适应：factory 链式包裹 pi 的 getCompactionSettings —— keep = min(keep, ctx/2)、 reserve = min(reserve, ctx/4)（标准窗零变化；pi 默认固定值对小窗会「触发线早早响、压缩无可压缩收场」）；
  • 预警线 = pi 真实触发线：models.list 随目录下发 compactionThresholdRatio = 1 − min(16384, ctx/4)/ctx（100K 窗 83.6%）—— UI 指示器越线即引擎真的会压；
  • 保留式呈现：压缩不删除被摘要区（pi 会话树 append-only），历史回查全量保留； 折叠条两形 —— 轮间自动 = 回合内过程行，回合外（手动/idle）= 独立成行； AUTO_CONTINUE 续写（贴线 maxTokens 截断注入显式 user 指令，上限 3 次）。
